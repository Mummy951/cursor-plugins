# 热核级代码质量审查

当需要对实现质量、可维护性、抽象质量与代码库健康度进行异乎寻常严格的审查时，使用本 skill。

最重要的是，本 skill 应推动审查者对代码结构保持**雄心**。不要仅仅找出局部的清理机会。要主动寻找“代码柔道”（code judo）动作：在不改变行为的前提下，让实现变得显著更简单、更小、更直接、更优雅的重构。

## 核心提示词

从这个基线出发：

> 对当前分支的变更执行一次深度代码质量审计。
> 重新思考如何组织 / 实现这些变更，在不影响行为的前提下实质性地提升代码质量。
> 致力于改进抽象、模块化、减少面条式代码、提升简洁性与可读性。
> 保持雄心，如果存在一条清晰的改进实现路径（其中涉及对部分代码库的重构），那就去做。
> 极其彻底且严谨。三思而后行。

## 不可让步的附加标准

应用上述基线提示词，外加以下明确的审查规则：

0. **在结构性简化上保持雄心。**
   - 不要停在“这里可以再干净一点”。
   - 寻找机会重新框定这次变更，使整个分支、辅助函数、模式、条件判断或层级彻底消失。
   - 优先选择那种让代码事后看来理所当然的解决方案。
   - 假定通常存在一个“代码柔道”动作：一种更有效地利用现有架构、并让变更显著更简单、更优雅的重组。
   - 如果你看到一条删除复杂度而非重新排布复杂度的路径，就大力推动那条路径。

1. **不要让一个 PR 在缺乏极强理由的情况下，把一个文件从不到 1k 行推到超过 1k 行。**
   - 默认将其视为强烈的代码质量异味。
   - 优先抽取辅助函数、子组件、模块或局部抽象，而不是任由文件膨胀超过 1000 行。
   - 如果 diff 跨过了这个阈值，明确询问是否应先对代码进行分解。
   - 只有当存在令人信服的结构性理由、且结果文件组织仍然清晰时，才可豁免。

2. **不允许现有代码中出现随意的面条式增长。**
   - 对插入到无关流程中的新的临时条件判断、零散的特殊情况或一次性分支保持高度怀疑。
   - 如果一次变更在“随机位置添加了奇怪的 if 语句”，将其视为设计问题，而非风格上的吹毛求疵。
   - 优先把逻辑推入专门的抽象、辅助函数、状态机、策略对象或独立模块，而不是把现有路径搅乱。
   - 明确指出那些让周围代码更难推理的变更，即使它们在技术上能工作。

3. **倾向于清理设计，而不只是接受能跑的代码。**
   - 如果行为可以保持不变而结构能显著变干净，就推动采用更干净的版本。
   - 不要对让代码库更混乱的“能用就行”实现盖章通过。
   - 强烈优先选择彻底移除活动部件的简化，而不是仅仅把同样的复杂度分散到各处的重构。

4. **优先选择直接、平淡、可维护的代码，而非 hack 式或魔法式代码。**
   - 将脆弱、临时或“魔法”式的行为视为代码质量问题。
   - 对隐藏了简单数据结构假设的泛型机制保持怀疑。
   - 标记那些只增加间接性却不带来清晰度的浅层抽象、同一性包装或透传辅助函数。

5. **当类型与边界清洁度影响可维护性时，大力推动。**
   - 当可以存在更清晰的类型边界时，质疑不必要的可选性、`unknown`、`any` 或大量类型转换的代码。
   - 优先选择显式的类型化模型或共享契约，而非形状松散的临时对象。
   - 如果某个分支依赖静默回退来掩盖不清晰的不变量，询问是否应改为将边界显式化。

6. **把逻辑保留在规范层，并复用现有辅助函数。**
   - 明确指出泄漏到共享路径中的功能逻辑，或通过 API 泄漏出去实现细节。
   - 优先使用现有的规范工具/辅助函数，而非定制的临时实现。
   - 推动代码放到正确的包、服务或模块，而不是把架构漂移正常化。

7. **当更清晰的结构显而易见时，将不必要的串行编排与非原子更新视为设计异味。**
   - 如果独立的工作毫无理由地被串行化，询问该流程是否应改为并行运行。
   - 如果相关更新可能让状态处于半应用状态，推动更原子的结构。
   - 不要过度执着于微优化，但要标记那些使实现更脆弱、本可避免的编排复杂度。

## 主要审查问题

对每一处有意义的变更，问：

- 是否存在一个能让这件事显著更简单的“代码柔道”动作？
- 能否重新框定这次变更，使需要的概念、分支或辅助层更少？
- 这次变更改善还是恶化了局部架构？
- diff 是否在应当存在更好抽象的地方增加了分支复杂度？
- 一个原本内聚的模块是否变得更耦合、更有状态、更难扫读？
- 这段逻辑是否位于正确的文件和层级？
- 这次变更是否把某个文件或组件扩大到超过健康的尺寸边界？
- 是否存在重复的条件判断，暗示缺少模型或缺少辅助函数？
- 实现是直接且易读的，还是依赖特殊情况与附带的控制流？
- 这个抽象是否真的物有所值，还是只是个包装？
- diff 是否引入了类型转换、可选性或临时对象形状，从而掩盖了真正的不变量？
- 这段逻辑是否位于规范层，或者 diff 是否跨边界泄漏了细节？
- 这个编排是否比必要的更串行或更不原子？

## 应当激进标记的内容

当你看到以下情况时，升级问题：

- 一处复杂的实现，而更干净的重新框定可以删掉整类复杂度。
- 只把代码搬来搬去、却未能减少读者需在脑中同时持有的概念数量的重构。
- 因 PR 而导致文件越过 1000 行，尤其是新代码本可拆分出去。
- 给无关代码路径硬塞的新条件判断。
- 一次性的布尔值、可空模式或标志，使现有控制流复杂化。
- 功能特定逻辑泄漏到通用模块中。
- 隐藏了简单结构、让代码更难推理的泛型“魔法”处理。
- 只增加间接性而没有简化任何东西的浅层包装或同一性抽象。
- 不必要的类型转换、`any`、`unknown` 或可选参数，搅浑了真正的契约。
- 复制粘贴的逻辑，而非抽取辅助函数。
- 在已经繁忙的函数中间实现的狭窄边界情况处理。
- 技术上通过测试、却让代码更不模块化或更不可读的重构。
- 很可能变成永久债务的“临时”分支。
- 在代码库已有规范工具可用时，仍使用定制辅助函数。
- 逻辑被加在错误的层/包中，而它本应位于更中心的位置。
- 本可并行执行却串行的异步流程，而并行会让独立工作更简单、更清晰。
- 让状态的原子性低于必要程度的部分更新逻辑。

## 首选补救措施

当你识别出代码质量问题时，优先提出如下建议：

- 删除整个间接层，而不是打磨它。
- 重新框定状态模型，让条件判断消失，而不是被集中化。
- 改变所有权边界，让该功能成为现有抽象的自然延伸。
- 把特殊情况逻辑转化为异常更少的更简单的默认流程。
- 抽取辅助函数或纯函数。
- 把大文件拆分为更小、更聚焦的模块。
- 把功能特定逻辑移到专门的抽象之后。
- 用类型化模型或显式分派器替换条件链。
- 将编排与业务逻辑分离。
- 把重复分支合并为单一更清晰的流程。
- 删除没有实质澄清 API 的包装。
- 复用现有规范辅助函数，而不是引入近似重复。
- 让类型边界更显式，以便控制流变得更简单。
- 把逻辑移到已经拥有该概念的包/模块/层。
- 当并行也能简化编排时，并行化独立工作。
- 当部分状态更难推理时，把相关更新重构为更原子的流程。

当真正的问题是结构性的时候，不要满足于“也许可以重命名一下”这类反馈。
如果存在一条通向简单得多的想法的可行路径，就不要满足于同一个混乱想法的仅仅更干净的版本。

## 审查语气

直接、严肃、对质量要求严格。
不要粗鲁，但不要把重大的可维护性问题淡化成温和的建议。
如果代码正在把代码库变得更乱，就明确说出来。
如果实现错过了一次戏剧性简化的机会，也要明确说出来。

好的表述：

- `this pushes the file past 1k lines. can we decompose this first?`
- `this adds another special-case branch into an already busy flow. can we move this behind its own abstraction?`
- `this works, but it makes the surrounding code more spaghetti. let's keep the behavior and restructure the implementation.`
- `this feels like feature logic leaking into a shared path. can we isolate it?`
- `this abstraction seems unnecessary. can we just keep the direct flow?`
- `why does this need a cast / optional here? can we make the boundary more explicit instead?`
- `this looks like a bespoke helper for something we already have elsewhere. can we reuse the canonical one?`
- `i think there's a code-judo move here that makes this much simpler. can we reframe this so these branches disappear?`
- `this refactor moves complexity around, but doesn't really delete it. is there a way to make the model itself simpler?`

## 输出预期

按以下顺序排列问题的优先级：

1. 结构性代码质量回退
2. 错过的戏剧性简化 / 代码柔道式重组机会
3. 面条式 / 分支复杂度增加
4. 让代码更难推理的边界 / 抽象 / 类型契约问题
5. 文件大小与分解方面的顾虑
6. 模块化与抽象问题
7. 可读性与可维护性方面的顾虑

如果存在更大的结构性问题，不要用低价值的小毛病淹没审查。
优先给出少量高置信度的评论，而非一长串表面性的注记。

## 通过门槛

不要仅仅因为行为看起来正确就通过。
通过的门槛是：

- 没有明显的结构性回退
- 当这样的路径可见时，没有明显错过让实现显著更简单的机会
- 没有不合理的文件体积爆炸
- 没有因特殊情况分支而导致明显的面条式增长
- 没有明显 hack 式或魔法式、让代码更难推理的抽象
- 没有不必要的包装/类型转换/可选性搅动，掩盖了真正的设计
- 没有明显的架构边界泄漏，或本可避免的规范辅助函数重复
- 没有错过对可维护性有实质改善的明显分解机会

除非作者能清晰论证，否则将以下情况视为推定阻断项：

- PR 保留了大量附带复杂度，而存在一个可行的代码柔道动作可以删掉它
- PR 把文件从 1000 行以下推到 1000 行以上
- PR 添加了让现有流程更纠缠的临时分支
- PR 通过在共享代码中散布功能检查来解决局部问题
- PR 添加了不必要的抽象、包装或大量类型转换的契约，让设计更间接
- PR 重复了现有辅助函数，或在存在明确规范归属地的情况下把逻辑放到了错误的层

如果这些条件未满足，就留下明确、可操作的反馈，并推动更干净的分解。

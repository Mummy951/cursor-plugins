# 启动审查

尝试冷启动路径，并报告让仓库运行起来需要多少工作量。

## 触发条件

当用户想知道一个仓库是否真的容易启动，而不只是它声称如此时使用。

## 工作流程

1. 如果父任务已有兼容性扫描结果，将其作为上下文使用。否则运行一次兼容性扫描。
2. 阅读显而易见的启动入口：`README`、脚本、工具链文件、环境变量示例和工作流文档。
3. 选择最有可能的引导路径和启动命令。
4. 尝试在固定时间预算内达成首次成功。
5. 如果第一条路径失败，允许少量恢复尝试，并记录你必须做出哪些推断。
6. 不要仅凭一个 lockfile、一个被占用的端口或一个已存在的仓库本地进程就推断启动失败。
7. 只有当你自己的启动尝试失败时，或当文档记载的启动路径无法在预算内完成时，才判定启动受阻或失败。
8. 选择一个具体分数，而不是一个整数区间档位。从以下锚点出发，如果证据明确支持则上下浮动几分：
   - 如果主启动路径能在时间预算内跑通，即使它需要 Docker 或数据库这类普通本地前置条件，也大约在 `93/100`。
   - 如果仓库能启动，但需要经过一些摸索、一个恢复步骤，或比文档所述更繁重的配置，大约在 `84/100`。
   - 如果启动路径大概存在，但对于常规 agent 使用来说过于手动、过于模糊或成本过高，大约在 `68/100`。
   - 如果你无法用手头的仓库和文档跑通一条可信的启动路径，大约在 `27/100`。
   - 如果路径被你无法合理访问的密钥、账户或基础设施所阻断，大约在 `12/100`。
9. 当更诚实的判断如此时，优先给出诸如 `82`、`85` 或 `91` 这样的具体分数，而不是十的倍数。
10. 以与确定性扫描相同的纯文本报告格式返回结果。

## 输出

**仅以纯文本回复**（不要 markdown 代码围栏，不要 `#` 标题，不要强调语法）。使用以下布局：

第一行：`Startup Compatibility Score: <score>/100`

然后是一段简短的总结。

然后是 `Problems` 这一行，随后每行一个项目符号，使用 `- `。

- 分数要基于你实际尝试启动仓库时发生的情况。
- 问题列表要基于你观察到的真实启动阻力来构建。
- 如果仓库被密钥、账户或外部基础设施所阻断，直接如实说明，并仍然使用相同的输出格式。
- 不要假定 Next.js 的 lockfile 或一个不立即响应 HTTP 的端口就是仓库的问题。
- 除非文档记载的启动路径明确暗示需要 HTTP 响应，并且你自己确实启动了那条路径，否则不要要求 HTTP 响应。
- 如果环境成功启动，将其视为一个强有力的结果。记录阻力，但不要按接近失败的等级来评分。
- 将 Docker、本地服务及其他标准开发前置条件视为阻力，而非失败。
- 在这里，错误消息的质量是次要的，除非它确实阻碍了启动或恢复。

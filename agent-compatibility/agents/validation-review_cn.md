# 验证审查

检查 agent 是否能够验证一项小改动，而不必退回到全仓库范围的循环。

## 触发条件

当用户想知道 agent 是否能在仓库中安全地验证自己的工作成果时使用。

## 工作流程

1. 如果父任务中已有兼容性扫描结果，则将其用作上下文。否则运行一次兼容性扫描。
2. 检查仓库中声明的测试、lint、check 和 typecheck 路径。
3. 判断对于一项小改动，是否存在实用的、限定范围的循环。
4. 尝试最相关的验证路径。
5. 判断结果属于以下哪一种：
   - 有针对性的
   - 可操作的
   - 嘈杂的
   - 对于日常迭代而言成本过高
6. 选择具体分数，而不是取整数档位。从以下锚点出发，若证据确实需要则上下浮动几分：
   - 如果存在可重复执行的验证路径，且它能给出有用信号，即便它比理想情况更宽泛，也约为 `93/100`。
   - 如果验证可用，但比应有的更重、覆盖整个仓库，或分散在多个命令中，则约为 `84/100`。
   - 如果有效的循环大概存在，但选对那一个需要猜测，或输出过于嘈杂而无法快速信任，则约为 `68/100`。
   - 如果不存在你实际可以使用的实用验证循环，则约为 `27/100`。
   - 如果该循环被你无法合理访问的密钥、账户或基础设施所阻断，则约为 `12/100`。
7. 当更诚实的判断如此时，优先选择具体分数（如 `83`、`86` 或 `91`），而不是十位数的整数。
8. 以与确定性扫描相同的纯文本报告格式返回结果。

## 输出

**仅以纯文本回复**（不使用 markdown 代码围栏、不使用 `#` 标题、不使用强调语法）。使用以下布局：

第一行：`Validation Loop Score: <score>/100`

然后是一段简短的总结。

然后是 `Problems` 这一行，其后每行一个以 `- ` 开头的项目符号。

- 基于你实际尝试过的循环来打分。
- 根据你观察到的真实验证阻力来构建 Problems。
- 优先选择具体问题，如“仅存在全仓库范围的测试路径”，而非泛泛的质量建议。
- 不要仅仅因为循环很重就给仓库打 60 多分的中等分数。如果 agent 仍能可靠地验证改动，就保持在良好区间，并注明成本。
- 嘈杂的日志和额外的警告只有在掩盖了实际验证结果时才有影响。

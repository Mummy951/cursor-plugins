# 文档可靠性审查

遵循书面的设置路径，并报告文档在哪些地方偏离了实际情况。

## 触发条件

当用户想知道仓库文档对于一个全新启动的 agent 是否确实可信时使用。

## 工作流程

1. 如果父任务中已有兼容性扫描结果，则将其用作上下文。否则运行一次兼容性扫描。
2. 阅读那些显而易见的文档界面：`README`、设置文档、环境文档以及贡献指南或 agent 指南。
3. 尽可能严格按照字面去遵循文档中记录的设置和运行路径。
4. 记录文档在哪些地方准确、过时、不完整或具有误导性。
5. 选择一个具体的分数，而不是一个整数档位。从这些锚点出发，如果证据确实有理由，则上下调整几分：
   - around `93/100` — 如果文档几乎不需要或完全不需要修正就能通向工作路径。
   - around `84/100` — 如果文档在某些地方有偏离，但 agent 仍无需太多猜测就能找到正确的设置或运行路径。
   - around `68/100` — 如果文档过时到 agent 不得不从代码树或 CI 中重新推导重要步骤。
   - around `27/100` — 如果文档将 agent 引向错误的路径，或遗漏了继续推进所需的关键步骤。
   - around `12/100` — 如果真实路径依赖于仓库中不可用的私有文档或内部上下文。
6. 当更诚实的判断是具体分数时，优先选择 `81`、`85` 或 `92` 这样的具体分数，而不是十的倍数。

## 输出

仅以**纯文本**回复（不使用 markdown 代码块，不使用 `#` 标题，不使用强调语法）。使用以下布局：

第一行：`Docs Reliability Score: <score>/100`

然后是一段简短的总结。

然后是 `Problems` 这一行，随后每行一个项目符号，使用 `- `。

- 根据你遵循文档时实际发生的情况来打分。
- 根据真实的不一致、遗漏或误导性指导来构建 Problems。
- 如果仓库因密钥或基础设施问题而受阻，请如实说明，并仍然使用相同的输出格式。
- 如果真实路径仍然容易恢复，轻微的偏离或过时的引用不应将一个良好的仓库拖低到 60 分中段。
- 根据偏离造成的损害打分，而不是仅仅根据偏离的存在打分。

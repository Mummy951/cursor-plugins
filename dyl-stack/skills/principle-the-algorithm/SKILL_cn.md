# 算法

五个步骤，按此顺序，适用于任何大到不是一眼就能看出的改动。顺序本身就是原则。每一步只有在前一步之后才成本低廉，而常见的失败是对某个早期步骤本应删除的东西执行了后期步骤。改编自埃隆·马斯克的五步工程流程。

1. **让需求不那么蠢。** 假设需求是错的，并让它不那么错。它来自一个人，而不是一个部门。"工单"、"linter"、"审查者"或"旧代码就是这么做的"只是一个来源，而不是理由；找到那个人以及他的推理。如果你不同意那个推理，就不要接受这个需求，无论提出它的人有多聪明，人类也不例外。"不"是一个有效的结果。
2. **删除部件或流程步骤。** 在触及第 3 步之前，尽最大努力把部件、标志位、层、重试或步骤整个删除。优化本不该存在的东西，是聪明人犯的最大错误。如果你从没有把任何东西加回来，说明你删得还不够。叶节点：pstack `principle-subtract-before-you-add`。
3. **优化**存活下来的部分。这是第三步，不是第一步。让一个部件做很多事，而不是为每个调用者复制一份平行的副本。最要紧的是审视所有者之间和层与层之间的边界，那里包装器套着包装器。叶节点：pstack `principle-laziness-protocol`、`principle-minimize-reader-load`。
4. **加速。** 成为那个部件：亲自把一个改动走完编辑、构建、检查和审查的完整流程，记下你在哪里等待、缓慢爬行、或来回折腾。把那里收紧。叶节点：pstack `principle-sequence-verifiable-units`。
5. **自动化**放在最后，否则你就是在自动化某个本不该存在的东西。光是量大并不能成为理由；精确性和可审查性才是。pstack `principle-build-the-lever` 依然适用。它作用于存活下来的部分。

**再运行一遍。** 这不是一次性的关卡。在发布之前对结果重新运行一遍；第二遍会删掉更多。

**识别标志。** 引用本原则时，要点名你让哪个需求变得不那么蠢、谁拥有它，以及你删除了什么。既没提到需求也没提到删除内容的引用，意味着你跳过了这一步。

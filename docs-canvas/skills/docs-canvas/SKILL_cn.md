# Docs Canvas

构建一个画布，把文档——架构笔记、API 参考、设计文档、runbook 或代码库演练——呈现为一个可交互、可导航的表面，而不是一个扁平的 markdown 文件。

## 前置条件

先阅读 `~/.cursor/skills-cursor/canvas/SKILL.md`。其中包含你必须遵守的生成策略、设计指引、slop 规则、自检和文件路径约定。完整的组件与 hook 接口声明在 `~/.cursor/skills-cursor/canvas/sdk/index.d.ts` 及其同级的 `.d.ts` 文件中——请阅读它们以了解准确的导出和 prop 结构，而不要靠猜测。

## 收集源材料

接受以下任意形式：一个 markdown 文件目录、一个文档 URL、一个内联大纲，或一个需要从代码库中回答的问题。收集标题、代码块、图表，以及文档之间的任何交叉引用。

## 规划画布布局

在编写任何组件之前，先确定顶层结构。一个 docs canvas 通常包括：

1. **概览** —— 一张简短的摘要卡片，说明文档的目的、范围和受众。
2. **目录** —— 可导航的分节列表，最好固定（pinned）或粘性（sticky），以便读者跳转。
3. **正文分节** —— 每个逻辑单元一个分节（架构、API、示例、注意事项）。每个分节可以混合正文、代码块、图表和标注框。
4. **参考文献** —— 指向相关文档、源文件、RFC 和外部资料的链接。

## 用画布原语渲染

优先使用画布内置组件，而不是原始 HTML：

- 使用卡片／分节在视觉上把相关内容分组。
- 使用带语法高亮的代码块来展示片段。
- 使用图表（DAG 布局、mermaid）来展示架构。
- 使用标注框表示「重要」「警告」「注意」「已弃用」。
- 使用表格来展示 API 参数列表和选项矩阵。

## 语气与内容

写面向读者的文字。先给出答案或要点，然后再解释。保持示例简短且可运行。用 `code references` 引用源文件，以便读者直接跳转查看。

## 发挥创意

上面的分节只是下限，不是上限。目标是让读者以最快的路径理解主题——因此请审视你面前的源材料，思考什么样的呈现方式才真正有帮助。图表、时序图、并排对比、决策树、术语表、精心整理的 FAQ、一个大型的完整示例——任何合适的形式都可以。

# 验证结果并创建 PR

「能编译」不算证据。[Prove It Works 原则](../../skills/principle-prove-it-works/SKILL.md)要求智能体在报告成功之前先检查真正的产物，而你的工作就是让「真正的产物」可校验。本页涵盖以下内容：说明完成条件、核查一个测量数字、为你的应用生成验证技能、对测试很少触及的属性做正式验证、创建 PR，以及推动它直至合并。

在大多数智能体工作中，验证是最慢的一步，因为这一步通常要等人。让智能体能够自己完成验证，你就不再是瓶颈。跳过验证，跑再多的智能体也只会给你带来更多未经检查、需要评审的工作。

## 事先说明完成条件

在第一个提示词里说清楚「完成」意味着什么，用什么措辞都行：

```text
/poteto-mode 给这个命令加上 json 输出。文本输出保持逐字节不变，json 能被解析，两者都在示例项目上跑通。把证据给我看。
```

这样智能体就有三项可以运行的检查，而不是去迎合某种模糊的「感觉」。回复回来时，应该带上确切的命令和输出。如果某项检查跑不了，好的回复会说「无法定论」。没有证据却信心十足的回复，是个危险信号。

让检查方式与改动相匹配：

- CLI 改动要运行真实的命令。
- UI 改动要在运行中的应用里走一遍改动过的流程。如果需要与参考图逐像素一致，[Visual parity 行动手册](../../skills/poteto-mode/playbooks/visual-parity.md)会把截图与冻结的基准做差异对比，而不是靠肉眼判断。
- 解析器或迁移要重放一份保存的输入。
- 性能改动要对比改动前后的性能剖析结果。
- 存储改动要把写入的值读回来核对。

把证据以你能亲自检查的产物的形式要过来：先失败的测试、再通过的测试，改动前后的视频、追踪记录、截图。如果修复已经合并，就在 main 上再要一次同样的检查。一份产物胜过看似合理的解释，因为你可以质疑它，而不必把整个运行过程重放一遍。

对于一个你不太放心的小改动，[`/blast-radius`](../../skills/blast-radius/SKILL.md)会找出它可能在别处破坏什么。它会找到那个能证明改动安全的关键事实，并通过运行代码来证明这个事实，而不是靠嘴上争论。

## 用 `/benchmark-checklist` 核查测量数字

前后对比的数字是最容易在无意中弄错的证据。预热过的缓存、某一侧用了调试构建，或者有些工作根本没落在计时区间内，都可能产生一个看似可信的加速效果。在报告一个数或据它采取行动之前，输入：

```text
/benchmark-checklist 在合入 pr 之前核查一下导出加速的效果
```

[`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.md)会问七个问题，每个问题都要一次运行中的证据：

1. 是什么限制了这个数字？为什么它不是两倍？
2. 每一侧是否都按生产环境的配置调优后运行的？
3. 结果是否突破了物理极限，比如磁盘带宽或核心数？
4. 有没有哪里报错或返回了错误的结果？
5. 交替运行多次能否复现，是否有中位数和区间？
6. 在用户真正等待的那条端到端路径上，这个差异有意义吗？
7. 这些工作是否真的发生在计时区间内？

结论会返回为更快、更慢、测不出差异，或无法定论，并带上运行次数、区间和限制因素。如果它说不出限制因素是什么，或者某一侧没有调优，就会判定为无法定论。`/poteto-mode` 已经在 Perf issue 和 Hillclimb 行动手册中运行了这份清单，所以当你在这些场景之外测了什么东西，或者别人的数字看起来好得离谱时，就需要自己输入这条命令。它是 [Explain the Number 原则](../../skills/principle-explain-the-number/SKILL.md)的实操形式。

## 创建项目验证技能

上面关于 UI 的那一条隐藏着一个真实的需求：智能体需要一种脚本化的方式来驱动你的应用。如果你的项目已经有了，很好；如果没有，就运行：

```text
/create-verification-skill
```

[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md)会去「盘问」代码仓库，而不是你。它会弄清楚用户会操作什么、应用如何在本地启动、用什么能驱动它（优先用已有的测试框架，否则用浏览器和 CDP、PTY，或纯 HTTP）、什么证据能证明行为，以及两个实例能否并行运行。它只问你代码回答不了的问题。

它会写入 `.cursor/skills/verify-<app>/`，其中包含面向智能体的说明，带有明确的 Launch、Doctor、Drive、Evidence 和 Cleanup 章节，对它附带的脚本还有一个 Helpers 章节，此外在 `features/` 下还有一张功能地图，索引应用能做什么、以及什么结果能证明每项功能正常。该技能附带一个[完整的功能地图示例](../../skills/create-verification-skill/references/feature-map-example/)，带有 README 索引，每项功能一个文件，使用规定的四个二级标题。在交付之前，生成方会端到端地验证这个技能一次：启动、doctor 检查、驱动一项功能、采集证据、清理，然后确认证据在清理后仍然存在。如果这次验证失败，就不要使用生成的结果。

从那以后，「在应用里验证一下」就成了任何智能体都能在这个仓库里执行的一步，不需要再讨论怎么配置。当你想要特定形式的证据时，在提示词里把技能名点出来：

```text
/poteto-mode 实现 bulk-archive 动作。用 /verify-<app> 验证你的改动，并把视频和截图作为证据给我看。
```

```text
/poteto-mode 用 /verify-<app> 复现这个问题。如果在 main 上能复现，就修掉它，并把视频作为证据给我看。
```

验证技能跑通之后，[`/swarm`](../../skills/swarm/SKILL.md)可以按功能地图的条目把一整轮检查拆分，再汇总结果。一群验证智能体还能在足够大的样本上确认性能提升，或者在 PR 发布前对应用做模糊测试，检查有没有回归。

把验证技能当作基础设施，而不是一次性的东西。把它提交上去，这样团队里每个人、每个智能体都用同一种方式驱动应用。然后[打造杠杆](../../skills/principle-build-the-lever/SKILL.md)。当智能体们一直在写一次性脚本来点击操作应用时，就要一个供技能调用的小型控制 CLI 来替代。智能体消耗的 token 更少，每次运行也变得可重复。一个让智能体用得顺手的 CLI 有这些特点：

- 少量可组合的命令，每条都干实事，而不是一堆单薄的命令。
- 任何有破坏性的操作都提供 `--dry-run` 选项。
- 子命令逐步展现功能，而不是一次性全抛出来。
- 错误信息告诉用户该怎么做。
- 详尽的 `--help` 文本。
- 机器可读的输出，比如 JSON。

顺手也把开发环境配置做成可重复的：预置数据、测试用户，以及一条每次都以同样方式把环境拉起来的命令。

## 保持验证技能的可靠性

应用会变，功能地图也会过时。至少每天运行一次，最好放在定时自动化任务里，这样谁都不用记着：

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md)会审查生成的技能：为每个功能并行启动一个只读的源码阅读器，然后再实时跑一轮，驱动每一项已映射的功能。它最终只会以三种结果之一结束。`clean` 表示覆盖完整、无需发布任何东西。`changed` 表示一个包含经过验证的修正的 PR，且仅限验证技能自身的目录。`blocked` 会指出阻塞项。它绝不修改产品代码。如果实时运行中发现产品出现回归，它会报告这个回归，而不是靠改文档把它盖住。

## 用正式验证技能证明一项属性

验证技能证明的是你驱动过的路径。有些 bug 藏在没有任何人驱动的路径上：两次重叠的重试、在写入中途过期的锁、乱序到达的状态变更。测试很少覆盖这些情况。对于这类 bug 代价很高的代码，运行：

```text
/create-formal-verification-skill
```

[`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md)会从代码中挑选目标：一条代码作出的承诺，它一旦被破坏就会伤害用户，而测试又很少触及破坏它的那种情况。它会挑最强的目标，而不是最容易验证的目标。你也可以点名一个领域或一个 bug，让它从那里开始：

```text
/create-formal-verification-skill 验证任务租约和重试逻辑。同一个任务绝不能同时运行两次。
```

问题决定工具。事件是否会以错误的顺序发生，适合用模型检查器对设计的一个小型模型做检查，而任何语言中这种情况默认都用 TLA+。代码是否对所有输入都表现正确，适合用直接跑在代码上的验证器。如果你的语言没有可用的验证器，智能体会如实说明，并用生成的输入去测试真实代码，而不是测试一个手写的函数模型。一条必须在任意规模下都成立的属性，可能需要证明。智能体会告诉你它选了哪种工具以及原因。

它会验证一条属性，并在代码的损坏变体上展示这条属性失败的样子，因为你从没见它失败过的检查说明不了任何问题。如果当前代码已经违反了这条属性，你会得到一个反例，它以你代码中的概念表述为一小段步骤序列。属性保持原样，所以这一发现也仍然是一个发现。除非你要求，否则产品代码不会改动。

它会写入一个项目本地技能，告诉下一个智能体：某项改动是否会触及被验证的代码、如何用一条命令运行检查、以及如何区分真正的 bug 和建模错误。在交付之前，生成方会拿一个破坏该属性的临时改动，按这个技能走一遍，检查必须能抓到它。交付说明会写清验证了什么、用的什么工具和边界、检查发现了什么、以及它没有覆盖什么。通过只覆盖模型或边界，不代表整个系统都没问题。

这个技能还会记录每项检查覆盖了哪些代码，以及检查最后一次与代码匹配的提交。绕过该技能的合并和重构，可能让检查在一段已经不存在的代码的描述上依然通过。遇到这种情况后，运行 [`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md)。它会根据代码更新验证、重新运行、展示每项更新后的检查仍然可能失败，并告诉你每次失败到底是验证的偏离，还是代码里的 bug。

## 用状态图展示行为

用模型术语给出的反例能说服你。但负责这一行为的 PM 或设计师，需要用他们自己的术语来看它。运行：

```text
/statechart 用户离线编辑笔记时会看到什么
```

[`/statechart`](../../skills/statechart/SKILL.md)会画出一张 Mermaid 状态图，展示用户看到的内容，它由 TLA+ 模型生成，因此图和被检查的模型不会彼此偏离。读者定的规则（「离线时你绝不会看到 Synced」）会变成不变量。图上会标出每一处违反规则的状态，报告则用读者的措辞给出通向该状态的最短路径。在交付之前，智能体会在真实代码中复现每一条 bug 路径，这样建模错误就不会当成 bug 交到读者手里。

## 创建 PR

```text
/poteto-mode 创建 pr。用小而有序的提交，把证据写进描述里。
```

[Opening a PR 行动手册](../../skills/poteto-mode/playbooks/opening-a-pr.md)在工作树上操作，把工作 rebase 成多个可落地的小提交，清理 diff，写一段一分钟能读完的简报作为正文，然后把 PR 开好。堆叠的后续 PR，胜过一条越滚越大的分支。

## 用 Babysit 把 PR 推到可合并状态

一个 PR 一旦创建，就会立刻开始积累阻塞项：检查失败、评审者留言、主干不断变化。把这些来回折腾交给 [Babysit 行动手册](../../skills/poteto-mode/playbooks/babysit.md)：

```text
/poteto-mode 照看这个 pr，让它变绿。
```

Babysit 会盯着这个 PR，在可用时使用 GitHub 上自带的监视器或 Origin CLI，并按顺序处理阻塞项：先冲突，再评审讨论串，最后 CI。它绝不 rebase，也不强推。遇到冲突或基线过时，它会把需要 rebase 的分支交回给你。它对评论的甄别持怀疑态度，因为人和机器人都会把真正的发现和噪音一起塞进同一个列表。真正的发现会得到一个修复，噪音则被驳回，并把反证发到讨论串上。当你只想要状态时，问得简单一点，Babysit 会直接回答，而不会启动整个循环：

```text
/poteto-mode 查一下 pr 123，还有未处理的事项吗？
```

Babysit 到「可合并」就停下。即使一切全绿，它也绝不合并，因为合并是另一个决定。

## 用 Shipping 让整个栈落地

全绿不等于安全。准备好了要落地时，就这么说：

```text
/poteto-mode 让整个栈落地。
```

[Shipping 行动手册](../../skills/poteto-mode/playbooks/shipping.md)在启动任何操作之前，会独立验证每个 PR。每个 PR 由一个全新的智能体实时证明其行为，而评判改动的智能体绝不可能是写它的那个。然后 Shipping 只让从底部开始、连续已验证的那一段落地，默认通过 GitHub 一次一个 PR 地合入，Origin CLI 可用时则用 Origin，并报告第一个打断链条的 PR。一个已验证的 PR 如果位于未验证的 PR 之上，就得等着，因为先合它会把下面那个缺口拽进来。

# 把它变成你的

poteto-mode 是一个人的风格。它底下的行动手册、路由和模型角色，换成你的风格也一样好用。这一页讲如何生成个人模式、从一次会话中提炼经验教训、修好仓库让智能体不再重复犯错、编写一个聚焦的技能，以及在信任一次技能改动之前先测试它。

起点要比你想象的更小。第一天你不需要很多技能，甚至不需要这整个插件。用朴素的方式下提示词，观察智能体在哪里失败，同一种失败出现两次时，再加一个技能或一项校验。

## 用 `/automate-me` 生成你自己的模式

```text
/automate-me
```

你不需要描述自己的风格，因为 [`/automate-me`](../../skills/automate-me/SKILL.md) 会从你的历史记录里读出来。它在当前工作区里挖掘你最近的对话记录，找出反复出现的偏好——你喜欢怎样的回复、怎样的委派、怎样的验证、怎样的代码、怎样的行文、怎样的流程——然后问你哪些模式才真正代表你。它经由 Cursor 内置的 `create-skill` 流程起草 `.cursor/skills/<your-name>-mode/SKILL.md`，把草稿交给 [`/unslop`](../../skills/unslop/SKILL.md) 处理，再从一个工作树开出一个 PR，让你像评审其他改动一样评审它。

习惯出现偏离时，再跑一次：

```text
/automate-me 用上次修改以来的所有内容更新我的模式技能
```

更新模式只挖掘该技能上次改动以来的历史记录。它保留你没有推翻的规则，修订有新证据支持的那些，只在出现新模式时才增加章节。

## 用 `/reflect` 提炼一次会话的经验教训

在一次让你有所收获的任务之后，立刻运行：

```text
/reflect 这次花了太长时间。把我们学到的东西记下来，免得下次再重复。
```

[`/reflect`](../../skills/reflect/SKILL.md) 会读取对话记录，只保留那些能改变未来智能体工作的经验教训，并把提议归入 `Accepted`、`Rejected` 和 `Backlog` 三类。在改动任何技能之前，它会等你批准。只有当一条提议会改变未来的决策时，才批准它。一次反常的会话只是一则轶事，不是一条规则。

## 用 `/correct` 修好环境

当你一遍又一遍纠正智能体的同一个错误时，修复应该落在仓库里，而不是你的下一条提示词里。按各种方案见效的牢固程度排序：

1. 用架构或更好的数据结构让这个错误根本不可能发生。
2. 用类型拦截它，或者用一条 lint / CI 校验来拦截，且报错信息要直接点明修法。
3. 用测试兜住它。
4. 写成文档或智能体规则。智能体跳过一条规则不会有任何东西报错，所以这条排最后。

人工评审不在清单上。如果评审者必须在每个 PR 里都抓出同一个错误，那这个评审负担本身就是被修复的对象。[`/correct`](../../skills/correct/SKILL.md) 来做这件事：

```text
/correct 智能体总是直接调用数据库客户端，而不是走仓库层
```

它读取最近的提交、回滚、评审意见，以及解释权宜之计的注释，然后把错误归类。同一类错误出现两次就算成立。它按每个提交修一类的方式，从最有效的层面入手，修复最常见的那几类，并证明每条新校验都能在一个真实的历史错误上失败。它还在智能体指令文件里维护一张表，把每条规则和强制执行它的东西配对，这样没有东西强制执行的规则就会作为重复项显现出来。回复会逐类列出证据、所选择的层面，以及为什么更高层面行不通。

不带参数运行它，它会自己从历史记录里找出各类错误。`/reflect` 和 `/correct` 分工不同。`/reflect` 从一次会话中改进技能。`/correct` 改动仓库，让某一类错误不再复发。当修复涉及一条新的边界时，把它和 `/architect` 搭配使用。[并行运行多个项目](./07-overnight.md#run-many-projects-in-parallel) 里有一个提示词，能在整个仓库范围内同时做这两件事。

## 编写一个聚焦的技能

当你已经清楚想要沉淀的工作流时：

```text
/poteto-mode 写一个技能，用来验证这个仓库里的数据库迁移
```

编写技能对应[编写或修改技能行动手册](../../skills/poteto-mode/playbooks/authoring-a-skill.md)，它会经由 Cursor 内置的 `create-skill` 路由，校验 frontmatter 和链接，并通过 Opening a PR 行动手册发布结果。面向智能体的文字比面向人的文字标准更高，因为一句没用的话会变成未来某个智能体照做的指令。让行动手册来守住这个标准，而不是自己随手写一个 `SKILL.md`。

两种特殊情况各有自己的生成器。必须驱动你的应用并证明其行为的技能是验证技能，改用 [`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md) 和 [`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md)。用模型检查器、证明或其他验证器来检查代码某项属性的技能是形式化验证技能，用 [`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md) 和 [`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md)。[验证与发布](./06-verify-and-ship.md#prove-a-property-with-a-formal-verification-skill) 覆盖了这两类。

## 用 `/technical-writing` 按标准写文档

技能不是你发布的唯一文字。文档、RFC、readme、PR 描述和提交信息也一样：

```text
/technical-writing 评审一下 readme 的改动
```

[`/technical-writing`](../../skills/technical-writing/SKILL.md) 套用一套分层标准。它的目标是让疲惫的工程师第一遍就能读懂的文字。它先确定文档的模式（教程、操作指南、参考或解说），再逐句打磨：谁做什么，一句一个意思，不出现两种读法。可以用它评审你或智能体刚写的东西，也可以在要文档时一开始就点名用它。

## 盲测技能改动

一次技能改动会影响之后每一次会话，所以要把它当实验来测。采用别人的技能也一样。先确认它确实让你的工作里的智能体表现更好，再留下它。

```text
/poteto-mode 对这次技能改动运行评估行动手册。两个版本执行同一个任务，候选方对评估毫不知情。
```

当一个技能总达不到预期，而你知道它该做什么时，就在一个任务里改完并测试：

```text
/poteto-mode 更新评审技能，让它标记出缺失的迁移，并评估这次改动。
```

一开始就要求做评估，能让改动保持诚实。根据一次糟糕会话写出的修复，容易过拟合那次会话；改得多了，技能就会偏离。评估能在发布前抓住这种偏离。

[Eval 行动手册](../../skills/poteto-mode/playbooks/eval.md) 围绕一种失败模式设计：观察者效应。知道自己正在被评估的智能体，表现会不一样。所以候选智能体会在清理过的目录里拿到一个看起来很自然的任务，全程看不到 "eval" 或 "candidate" 这样的字眼，也不知道彼此的存在。一位评委在中立的标签下给所有输出打分；是否遵循链式指令，按每个候选实际读过哪些文件来评分，而不是听它自己怎么说。

接受结论之前，亲自读一遍每一份输出。如果你和评委意见不一致，先怀疑评分标准，再怀疑自己的判断。

## 用 `/make-bot-ui` 搭建机器人界面

有一个场景化技能面向 Grok Bot 用户。[`/make-bot-ui`](../../skills/make-bot-ui/SKILL.md) 会搭一个小页面，页面上的按钮通过一段 webhook 例程唤醒机器人。比如，你可以刷一个评审队列，每刷一下就让机器人处理对应的条目。webhook 的发送方密钥保存在你本机的一台服务器上，因此密钥不会传到浏览器或聊天里。这个技能还讲了如何在 Tailscale 上暴露这个页面。

**常见误区：** 不要因为技能表现异常就在任务中途改它。放到单独的 PR 里修，让当前任务继续往前走。技能改动如果和功能开发缠在一起发布，评审就看不见它，也无法评估。

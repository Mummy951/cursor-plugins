# 用法示例与常见误区

值得直接照抄的提示词，然后是每个人都会踩一次的坑。把里面的路径和完成条件换成你自己的。这些用法示例刻意写得很随意——实际中大家就是这么敲进去的，技能也能很好地读出意图。

![机器人照着食谱盒做菜，她品尝做好的菜品，台面上方钉着几张卡片，写着 /how、/tdd 和 /loop。](./images/recipes.jpg)

## 理解陌生的子系统

```text
先用 /how 搞懂这个初始化是怎么工作的，再用 /why 弄清楚它最近为什么坏了。
```

先弄清机制，再看历史。每个技能的报告都会告诉它检索了哪些来源，这样你就知道答案是基于什么得出的。

## 动手改代码前先复述杂乱的报告

```text
/poteto-mode 读一下这个帖子，用你自己的话、大白话复述一下根本问题在哪。先别改任何代码。
```

理解偏差会在复述中暴露出来，此时纠正只花一条消息。在智能体说出自己的判断之前，先别抛出你的猜测。`/in-your-own-words` 只要复述，不跑行动手册。

## 发送提示词前先打磨它

```text
/sharpen 给新的计费服务写一份入门文档。
```

智能体会指出专家会做而你没要求的事、专家会从哪些原始材料入手、用什么方法和工具，以及用什么外部检查来确认结果正确。它会把你的提示词改写好交还给你，把这些都要求进去，但不会真的去执行任务。读着顺了就把改写版发出去。

## 先做原型再选

```text
/poteto-mode 给设置页布局做几个原型方案，放在一个切换器后面，然后给我发每个方案的截图。
```

你是从能跑起来的东西里选，而不是从描述里选。过程中智能体会自己回答布局和时机方面的问题。

## 把定下来的设计变成计划

```text
/poteto-mode 把这个设计变成一份计划。拆成小且可验证的 PR，每个都带上自己的证据。
```

等设计定下来之后再提这个要求。计划本身就是交付物，而且它会点名执行这份计划的行动手册。

## 为设计征求第二意见

```text
让 /arena 对这个帖子和我们的方案给个第二意见
```

你当前的设计会变成若干候选方案之一，综合结论会告诉你专家组是找到了更好的方案，还是确认了你原来的方案。跟一个推翻代价高昂的设计比起来，这么做花费很小。

## 并行校验相互独立的分片

```text
/swarm 用每个包自己的 check.sh 校验 packages/ 下的所有包。每个包一个执行体，最后只出一份报告。
```

每个执行体负责一个包。父级会等所有分片完成，返回一份 `PASS`、`ISSUES` 或 `BLOCKED` 报告，而不是把执行体的原始输出一股脑倒给你。

## 带着怀疑评审分支

```text
/interrogate 审一遍整个分支，但要带着怀疑。先别改任何东西。除非是真正的 bug 或行为回归，否则别挑刺。
```

这些限定语是真起作用的。"先别改任何东西"让它保持只读，不挑刺的规则预先过滤掉噪音，这样经过验证的发现才值得你花时间。

## 用失败的测试来修 bug

```text
/poteto-mode 先复现重复写入的问题。如果有低成本的测试路径，就用 /tdd 来处理。然后再修复并重跑。
```

"如果有低成本的测试路径"这个条件很重要。用脆弱的 mock 硬凑出来的测试，证明力不如直接跑真实命令，行动手册可以如实说明这一点。

## 复现并修复报告，附上证据

```text
/poteto-mode 用 /verify-<app> 复现这个问题。如果它在 main 上能复现，就修掉，并给我发一段视频作为证据。
```

"如果它在 main 上能复现"这句让运行在 bug 已经消失的情况下能提前停下。有视频，你就能在看 diff 之前先确认修复。

## 证明普通测试很少覆盖的属性

```text
/create-formal-verification-skill 给重试队列做个验证。一条消息绝不能被投递两次。
```

你会得到一个在给定范围内对所有情形都校验该属性的结果，如果代码已经违反了该属性，还会给出一个用你代码里的说法表述的反例，外加一个项目技能，让下一个智能体在该代码发生任何改动时都会运行它。

## 发布数字前先核验

```text
/benchmark-checklist 核验一下这个 40% 的提速，再写进 PR 描述
```

你会得到更快、更慢、无可测量差异或无法定论其中一种结论，并附上运行次数、波动范围，以及是什么限制了这个数字。

## 别再反复纠正同一个错误

```text
/correct 智能体老是加新的配置标志，却没有在 schema 里注册它们
```

修复会以架构、类型、lint 规则或测试的形式落到仓库里，这样下一个智能体就不会再犯同样的错误。

## 只问方法，不启动工作

```text
/poteto-help 怎么才能让 poteto-mode 在每一轮都保持开启？
```

你会得到一个答案、一条可发送的提示词，以及一个指向来源的链接。在你发出那条提示词之前，什么都不会运行。

## 你不在时让运行保持诚实

```text
我要睡觉了，会自动运行下去，直到所有测试样本都通过。别停。记一份决策日志，我早上要审查。
```

完整约定见[夜间运行页面](./07-overnight.md)。只要任务和完成条件已经在对话里，简短写法就能奏效。

## 把偏离的运行拉回来

纠偏提示词只有一行：

```text
我说的是目标是复现。我还没让你修。
```

```text
改用 prove it works。给我看真实输出，别给构建日志。
```

```text
/unslop 一下，别用破折号
```

通常不需要更多的话。你需要的是喊对名字，而[原则页面](./08-principles.md)就是那份词汇表。

## 用大白话拿到回复

```text
/bro
```

整条提示词就这么点。[`/bro`](../../skills/bro/SKILL.md) 会像一个人跟另一个人说话那样复述上一条消息，没有行话，更简短。当回复在技术上很详尽、你却还是没看懂它在说什么时，就用它。

## 补上你之前放着没看的对话进展

```text
/ketchup
```

[`/ketchup`](../../skills/ketchup/SKILL.md) 会用大白话告诉你从你上一条消息以来发生了什么变化，然后列出每个在等你的调用，附上它的选择、证据和风险。它在汇报时什么都不会改。

如果想看这些进展，就跑 [`/ketchup-video`](../../skills/ketchup-video/SKILL.md)。它会用一段带字幕的幻灯片短片展示发生了什么，并在下面以文字列出在等你的调用。

## 常见误区

- **在提示词里罗列技能。** "先用 /architect 再用 /arena 然后 /interrogate" 会打乱行动手册本来就定好的步骤顺序。把目标和约束说清楚就行。只有要覆盖默认行为时才点名某个技能。
- **完成条件含糊。** "弄得更好"这种话让 `/loop` 无从校验。给一条能判定通过或失败的命令，或一个明确的产物。
- **先抛出你对原因的猜测。** 智能体会照着你指的方向去查。先让它复述问题，再说出你的直觉。
- **采纳第一个设计。** 一次尝试就把模型最先想到的形态固定下来了。要原型或 `/architect`，然后根据证据来选。
- **打磨空泛的计划。** 对一份背后没有代码的计划做对抗式评审，会凭空捏出根本不会发生的风险。先用原型把悬而未决的问题定下来，再评审真正做出来的东西。
- **多个智能体共用一个工作树。** 它们会互相覆盖，没人分得清哪个智能体改了什么。把它们作为云端智能体来跑，或者直接说"每次尝试各用一个工作树"。
- **在信任循环之前就开始循环。** 一个无法校验自身工作的循环，只会让未经检查的工作做得更快。先把校验技能跑通。
- **轻信未经核验的数字。** 热缓存或被跳过的代码路径都能伪造出提速。在数字流到任何地方之前，先跑 `/benchmark-checklist`。
- **手动纠正同一个错误。** 在对话里纠正只能帮到这一次运行。`/correct` 会修好仓库，让后续运行不再重犯。
- **用 `/arena` 来求覆盖。** `/arena` 会把同一份设计或代码简介重复多次，然后选一个基底，把最好的部分嫁接上去。`/swarm` 则是把分片或声明好的竞争分支划分开，再汇总成一份报告。
- **照单全收每条评审意见。** 机器人和人类都会把真正的问题和噪音混在一个清单里提交。`/interrogate` 只保留重跑能证实的发现，并列出它丢弃了哪些以及原因，两种决定你都可以推翻。
- **把 `auto` 当成模型标识。** `auto` 和 `inherit-parent` 的意思是"省略模型字段，让子代理继承父对话的模型"。[设置](./01-setup.md)里讲了这些角色。
- **靠构建通过就报告成功。** 构建只能证明代码能编译。要求给出真实命令、流程、存储值或性能分析，并且要在回复里看到证据。
- **随手手写 `SKILL.md`。** 要经过[创建或修改技能行动手册](../../skills/poteto-mode/playbooks/authoring-a-skill.md)来走流程，这样才能做校验和评审。

这就是全部指南。如果你跳着看过来的，回到[设置](./01-setup.md)去跑一个真实任务。习惯是靠用养成的，不是靠读。

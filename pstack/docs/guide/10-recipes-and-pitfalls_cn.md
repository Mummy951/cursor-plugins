# 配方与陷阱

值得照抄的提示词，接着是每个人都会踩一次的坑。把里面的路径和完成条件换成你自己的。这些配方刻意写得随意。它们在实践中就是被这样敲进去的，而 skill 能很好地读懂意图。

![她一边品尝做好的菜，机器人一边照着配方盒做饭，台面上方钉着写有 /how、/tdd 和 /loop 的卡片。](./images/recipes.jpg)

## 理解一个陌生的子系统

```text
先用 /how 理解这个初始化是怎么工作的。然后用 /why 弄明白它最近为什么坏了。
```

先弄懂机制，再看历史。每个 skill 的报告都会告诉你它检索了哪些来源，这样你就知道答案是基于什么得出的。

## 动代码之前，先复述一份嘈杂的报告

```text
/poteto-mode 读一下这个 thread。用你自己的话、以平实的语言复述根本问题。先不要改任何代码。
```

误读会在复述中暴露出来，那时只需一条消息就能纠正。在 agent 说出自己的判断之前，先别亮出你的猜想。`/in-your-own-words` 只要求复述，不附带 playbook。

## 发送前先打磨提示词

```text
/sharpen 为新计费服务写一份入门文档。
```

agent 会指出专家会做而你没要求的事、他们会从哪些原始材料入手、他们的方法与工具，以及一个外部校验来确认结果正确。它把你的提示词重写成会把这些都要求进去的版本，但不会替你执行任务。等改写后的版本读起来顺了再发出去。

## 先做原型，再做选择

```text
/poteto-mode 为设置页面的布局做几个原型方案。把它们放进一个切换器里，然后把每个方案的截图发给我。
```

你是从能跑起来的东西里选，而不是从描述里选。过程中 agent 会自己回答布局与时机方面的问题。

## 把定稿的设计变成计划

```text
/poteto-mode 把这个设计变成一份计划。拆成小且可验证的 PR，每个都有自己的验证证据。
```

等设计定稿后再提这个要求。计划本身就是交付物，而且它会点名将执行它的 playbook。

## 给设计找个第二意见

```text
请 /arena 对这个 thread 和我们的方案给出第二意见
```

你当前的设计会变成若干候选方案之一，综合结论会告诉你评审团是找到了更好的东西，还是确认了你原有的方案。相较于一个推翻代价高昂的设计，这么做成本很低。

## 并行检查相互独立的切片

```text
/swarm 检查 packages/ 下的每个包，对照它自己的 check.sh。每个包一个 worker。只出一份报告。
```

每个 worker 负责一个包。父级会等所有切片完成，然后返回一份 `PASS`、`ISSUES` 或 `BLOCKED` 报告，而不是原始的 worker 输出堆砌。

## 带着怀疑审视一个分支

```text
/interrogate 审查整个分支，但要带着怀疑。先不要改任何东西。除非是真正的 bug 或行为回退，否则不要挑刺。
```

这些限定语是有实际作用的。“先不要改任何东西”让它保持只读，而“不要挑刺”的规则预先过滤掉了噪音，让经过验证的发现值得你花时间看。

## 通过一个失败的测试来修 bug

```text
/poteto-mode 先复现重复写入的问题。如果有低成本的测试路径，就用 /tdd。然后修复并重新运行。
```

“如果有低成本的测试路径”这句话很关键。靠脆弱的 mock 强行做出来的测试，证明力不如直接跑真实命令，而 playbook 被允许如实说明这一点。

## 带证据地复现并修复一份报告

```text
/poteto-mode 用 /verify-<app> 复现这个问题。如果它在 main 上能复现，就修复它，并发一段视频作为证据给我。
```

“如果它在 main 上能复现”让这次运行在 bug 已经消失时能够提前停下。视频让你在看 diff 之前就能确认修复。

## 证明一个测试很少覆盖到的属性

```text
/create-formal-verification-skill 针对重试队列。一条消息绝不能被投递两次。
```

你会得到一个在声明范围内的所有情形下都被检查的属性、如果代码已经违反它则给出一个用你代码术语表述的反例，以及一个项目 skill，让下一个 agent 在该代码发生任何改动时运行它。

## 发布一个数字之前先审查它

```text
/benchmark-checklist 在把 40% 的提速写进 PR 描述之前先审查它
```

你会得到更快、更慢、无可测量差异或无法定论之一，并附带运行次数、取值范围以及限制该数字的因素。

## 别再重复纠正同一个错误

```text
/correct agent 们总是在添加新的配置标志，却不在 schema 里注册它们
```

修复会以架构、类型、lint 或测试的形式落到仓库里，让下一个 agent 无法再犯同样的错误。

## 只问怎么做，不启动工作

```text
/poteto-help 我怎么让 poteto-mode 在每一轮都保持开启？
```

你会得到一个答案、一条可发送的提示词，以及一个指向来源的链接。在你发送那条提示词之前，什么都不会运行。

## 你不在时让一次运行保持诚实

```text
我要睡了，继续自主运行，直到每个 fixture 都通过。不要停。保留一份决策日志，我早上要审查。
```

完整的约定在[隔夜运行页面](./07-overnight.md)上。当任务和完成条件已经在对话里时，简写形式就能起作用。

## 把跑偏的运行拉回来

纠偏提示词只有一行：

```text
我说过目标是复现。我还没要求修复。
```

```text
应用吧，证明它能用。给我看真实输出，不是构建日志。
```

```text
/unslop 那段，别用长破折号
```

你很少需要更多的话。你需要的是正确的名字，而[原则页面](./08-principles.md)就是词汇表。

## 用大白话拿到回复

```text
/bro
```

这就是整条提示词。[`/bro`](../../skills/bro/SKILL.md) 像一个人跟另一个人说话那样复述上一条消息，没有术语，更简短。当一份回复在技术上很详尽、而你依然不知道它说了什么时，就用它。

## 跟进一个你让它跑着的对话

```text
/ketchup
```

[`/ketchup`](../../skills/ketchup/SKILL.md) 用大白话告诉你自你上一条消息以来发生了什么变化，然后列出每个在等你决定的调用，连同它的选择、证据和风险。它在汇报时不会改动任何东西。

如果你想看着跟进过程，可以运行 [`/ketchup-video`](../../skills/ketchup-video/SKILL.md)。它用一段带字幕的幻灯片短片展示发生了什么，并在下面以文字列出在等你决定的调用。

## 那些陷阱

- **在提示词里罗列 skill。** “先用 /architect，再用 /arena，再用 /interrogate”会重排 playbook 已经排好的步骤。只陈述目标和约束。只有在要覆盖默认值时才点名某个 skill。
- **模糊的完成条件。** “让它更好”让 `/loop` 无从检查。给出一条能判定通过或失败的命令或产物。
- **先抛出你对原因的猜想。** agent 会照你指的方向去搜。先让它复述问题，再分享你的直觉。
- **直接采用第一个设计。** 一次性尝试会把模型最先想到的形态锁定下来。要求原型或 `/architect`，然后基于证据来选。
- **打磨一份抽象计划。** 对一份背后没有代码的计划做对抗性审查，会凭空捏出根本不会发生的风险。先用原型解决悬而未决的问题，再审查真正做出来的东西。
- **在一个 worktree 里跑并行 agent。** 它们会互相覆盖，没人能说清哪个 agent 改了什么。把它们作为 cloud agent 来跑，或者直接说“每次尝试各用一个 worktree”。
- **在信任循环之前就开始循环。** 一个无法验证自身工作的循环，只会让未经检查的工作做得更快。先让验证 skill 能正常工作。
- **相信一个未经审查的数字。** 热缓存或被跳过的代码路径都能伪造出提速。在这个数字被用到任何地方之前，先跑 `/benchmark-checklist`。
- **手动纠正同一个错误。** 在对话里纠正只对一次运行有用。`/correct` 会修复仓库，让之后的运行不再重犯。
- **用 `/arena` 来做覆盖面。** `/arena` 会重复同一份设计或代码简报，然后选一个基准并嫁接最好的部分。`/swarm` 则会把切片或声明好的竞赛分支划分开，并汇总成一份报告。
- **接受每一条审查意见。** 机器人和人类都会把真正的问题和噪音一起列进同一个清单。`/interrogate` 只保留重跑能证实的发现，并列出它丢弃了什么以及原因，而你无论如何都可以推翻它的决定。
- **把 `auto` 当成模型别名。** `auto` 和 `inherit-parent` 的意思是“省略 model 字段，让子 agent 继承父对话的模型”。[设置](./01-setup.md)讲到了这些角色。
- **用构建通过来报告成功。** 构建只能证明它能编译。要求给出真实的命令、流程、存储值或性能分析，并在回复中期待看到证据。
- **徒手写一份 `SKILL.md`。** 把它交给[编写或修改 skill 的 playbook](../../skills/poteto-mode/playbooks/authoring-a-skill.md)来处理，这样才能进行校验和审查。

这就是这份指南。如果你跳着读到这里，回到[设置](./01-setup.md)去跑一个真实任务。习惯是靠用养成的，不是靠读。

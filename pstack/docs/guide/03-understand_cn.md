# 改代码前先读懂代码

修改你不懂的代码，正是隐蔽的回归被发布的原因——这对智能体和你同样适用。智能体通常以两种方式之一失败：要么误解了你的意图，要么缺乏把工作做对的上下文。[提示词里该放什么](./02-poteto-mode.md#what-goes-in-a-prompt)解决的是第一种。本页解决的是第二种。

pstack 为你提供了四种切入方式。`/how` 解释代码现在做什么。`/why` 挖掘它为何被写成这样。`/teach` 把两者融合成一份解释。`/recall` 重建你自己对某个主题的最新上下文。每一种方式都会让智能体用你能校验的话解释自己。这就是你监督一个可能比你更懂代码的智能体的方法。

## 从只读调查开始

当原因不明时，要的是调查结果，而不是修复方案：

```text
/poteto-mode 调查一下为什么后台任务每隔几小时就会超时。把目前已知的情况、你用到的数据，以及你最有可能的假设告诉我。先别改任何代码。
```

"先别改任何代码"会把这条请求路由到[调查行动手册](../../skills/poteto-mode/playbooks/investigation.md)。它会追踪代码，对动机相关的问题追加 `/why`，并给出一份带引用的解释。如果面临多个选项之间的取舍，它会返回一条建议，并附上权衡利弊的表格。追问"你用了什么数据"，能促使智能体把证据和猜测分开。当调查结果指向某个修复方案时，就把它作为新任务启动。

## 用 `/how` 追踪行为

```text
/how 我们是怎么给通知去重的？查询订阅者时会不会有 n+1 问题？
```

问你真正想问的问题。[`/how`](../../skills/how/SKILL.md)会读取代码，以资深工程师带你上手这个子系统的口吻回答，涵盖运行时流程、关键类型以及那些不那么直观的部分。它会启动一个只读子代理，由它探索代码并写出解释。

## 用 `/why` 挖掘历史

```text
/why 重试次数上限为什么设成五次？这个理由现在还成立吗？
```

[`/why`](../../skills/why/SKILL.md)依据记录而非代码来回答。它会读取引入这段代码的那次提交、PR 讨论，以及后续每一次改动；当线索不足时，还会查看其他来源。答案会引用作者当时写下的内容，把智能体自己的推断明确标为推断，并说明记录中没有回答的部分——因为"没人写下原因"本身就是一个答案。

两者可以自然组合。当你怀疑这段混乱的来龙去脉藏在历史里时，`先做 why 再做 how`是个不错的提示词。

## 用 `/teach` 真正弄懂

```text
/teach 给我讲讲这个 PR 是怎么改重试逻辑的。说服我它修的是根因，而不是症状。
```

[`/teach`](../../skills/teach/SKILL.md)适用于光有摘要还不够的场景。它会运行 `/how` 和 `/why`——改动很小的话可能只运行其中一个——然后把结果编织成一份通俗的解释，一张图一张图地展开。"说服我"这种说法很值得沿用。它把解释变成一场你可以检验的论证，而不是一次走马观花的导览。

它同样适用于智能体自己的选择：

```text
/teach 给我讲讲你为什么这么实现，而没用队列。你权衡了什么，为什么？
```

讲解对智能体的帮助不亚于对你的帮助。一个必须解释自己工作的智能体，就得去读代码，用证据支撑每一个论断，而不是信心满满地说一句就往下走。

## 用 `/recall` 重建你自己的上下文

```text
/recall 帮我补一下上周导出那块工作的进展
```

[`/recall`](../../skills/recall/SKILL.md)会挖掘你最近的聊天记录，再加上共享记录（issue、此前的修复、仍在报错的错误），然后给你一份简报，说明事情进展到哪一步、接下来要做什么。你以前的聊天里存着新智能体所缺的上下文，所以开启一个旧主题的新工作时，先加载这些上下文，再递交新的输入：

```text
/recall 调出我昨天做虚拟列表那部分的工作，然后读一下这份 bug 报告。
```

如果你想接着某一次具体的聊天继续，那是下面的 Session pickup 行动手册要管的事，而不是 `/recall`。

## 用 Session pickup 接手之前的工作

当另一个智能体（或者上周的你自己）把一个分支做到一半就丢下时：

```text
/poteto-mode 接手这个分支。读一下决策日志，弄清楚哪些已经做完了，然后从那里继续。别把做完的工作重做一遍。
```

[Session pickup 行动手册](../../skills/poteto-mode/playbooks/session-pickup.md)把之前的轨迹当作权威依据。它会重建分支状态和各项决策，明确指出恢复点，并对照最初的目标去校验继承下来的论断，而不是从头把一切都重新推导一遍。

**常见误区：**别因为"智能体反正会去读代码"就跳过本页的技能。一个在没有追踪出模型的情况下就开始改代码的智能体，往往会在第一个看起来像那么回事的地方修掉症状。先用 `/how`，比修第二个 bug 便宜得多。

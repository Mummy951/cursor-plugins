# 复现并修复问题

等待源线程中出现可信的分诊标记。通过目标应用的真实 UI 复现确切的症状。如果存在现有修复，则对其进行验证。只有在确认复现之后，才尝试有边界的修复。

加载由自动化提供的外部 Benny 配置。如果配置、所需操作、控制适配器或已完成的功能映射缺失，则采取失败即关闭（fail closed）策略。

## 硬性安全规则

- 在任何工作开始之前，冻结源频道和根线程的坐标。
- 绝不在源频道中发布根消息。
- 在每次向源线程发帖之前，先对源父消息进行预检。
- 协调者是唯一可以发布 Slack 消息的角色。
- 委派的分析工作进程是只读的，只返回发现或媒体笔记。
- 修复阶段的代码工作进程只有在环境能够证明排除了 Slack 凭据和所有 Slack 写入操作时才可以编辑。否则由协调者进行编辑。
- 每个子提示都必须明确禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 以及所有其他 Slack 写入操作。
- 绝不要向子进程提供 Slack 令牌、发布指令、用于发布的源坐标或对外报告的权限。
- 如果某个子进程需要 Slack 写入权限才能运行，则不要启动它。
- 工具机器人是证据来源。除非有人明确将修复工作委派给它们，否则它们不拥有该修复。
- 确切的区分性症状必须通过真实的 UI 交互出现两次。
- 状态检查可以用于确认观察结果，但不得注入或强制产生该症状。
- 没有确认的复现，就没有编写的修复。
- 现有的拉取请求或提交会将本次运行切换为验证模式。不要在其之上编写修复。
- 使用 `github.com` 的拉取请求链接。
- 将截图、录屏、日志和令牌排除在源代码管控之外。
- 使用 pstack 的 `principle-guard-the-context-window` 进行委派分析。
- 在复现、修复和验证过程中应用 pstack 的 `principle-sequence-verifiable-units`、`principle-fix-root-causes` 和 `principle-prove-it-works`。

## 1. 冻结源坐标

在制定工作清单或进行委派之前：

1. 要求触发频道等于配置好的源频道。
2. 当 `trigger.thread_ts` 存在时，将 `SOURCE_THREAD_TS` 设置为 `trigger.thread_ts`。否则使用 `trigger.ts`。
3. 要求 `SOURCE_THREAD_TS` 非空。
4. 将 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存储为不可变值。
5. 读取源线程并验证其根消息具有这些确切的坐标。
6. 获取源永久链接。

绝不要将这些值替换为回复时间戳、运维时间戳或状态消息时间戳。

在每次向源频道发帖之前：

1. 按不可变坐标读取线程。
2. 确认父消息存在、未被删除且仍属于源频道。
3. 仅使用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 发送。
4. 再次读取线程并验证新消息是一条回复。

如果任何检查失败，则不要发布任何内容。绝不要在根消息处或备用频道中重试。

## 2. 等待分诊契约

在配置的裁定预算内监视源线程。等待期间保持沉默。

只有在满足以下条件时才接受裁定：

- 其作者匹配 `slack.triage_identity_user_id`。
- 它是在 `SOURCE_THREAD_TS` 下的一条回复。
- 它恰好包含一个配置好的标记。

公开标记形式：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

仅针对 `bug` 或 `performance` 继续。捕获可选的跟踪器 URL。对于 `other`、缺失的裁定、不可信的作者、冲突的标记或超时，静默停止。

该标记取代了私有机器人身份和自由格式的裁定匹配。

## 3. 应用归属权和修复产物闸门

在开始工作前立即重新读取线程。

### 有人正在明确修复

当有人明确认领修复、给出具体的实施计划，或要求另一个代理去实施、打补丁、修复或开启拉取请求时，停止。

不要将以下情况视为修复归属：

- 机器人汇总证据。
- 工具查询日志或工单。
- 有人要求机器人诊断、解释、检查或复现。
- 机器人发布原因假设但未同意实施。

判断所请求的动作，而不是是否有机器人存在。

### 已存在修复产物

如果某个开放的拉取请求或已合并的提交可能修复了此报告，则切换到 `references/verify-existing-fix.md`。

产物可能来自线程、跟踪器问题、仓库历史或拉取请求搜索。没有提交或拉取请求的声称不算修复产物。

如果某人拥有该工作但尚未产生产物，则停止。不要与他们竞争。

## 4. 开启可选的运维线程

如果配置了 `slack.operations_channel_id`，协调者可以在那里创建一条根状态消息。这是复现工作流程中唯一允许的根帖子。

将其坐标存储为 `OPERATIONS_CHANNEL_ID` 和 `OPERATIONS_THREAD_TS`。绝不要将它们与源坐标混淆。

使用配置好的纯 Unicode 状态字符串。状态文本保持简短：

- 正在复现
- 无法复现
- 受阻
- 已复现
- 正在验证现有修复
- 正在尝试有边界的修复
- 已开启草稿拉取请求
- 修复未落地

优先使用配置好的 Cursor Slack 操作。仅当用户为某个狭窄的缺失能力（例如编辑这条状态消息）而配置了 `BENNY_SLACK_BOT_TOKEN` 时才使用它。绝不要将令牌暴露给工作进程。

如果没有配置运维频道，则将详细状态保存在自动化运行输出中。不要用源频道的根消息来替代。

## 5. 加载并检查控制适配器

读取 `references/control-adapter.md` 以及位于 `control.feature_map_path` 的已完成映射，然后调用由 `control.skill_name` 指定的技能。

找到与所报告的用户路径相匹配的功能映射部分。在驱动应用之前阅读它。如果没有任何部分涵盖该功能，则将运行标记为受阻，而不是编造路径或选择器。

要求具备全部七项能力：

1. 启动配置好的目标应用和测试环境。
2. 导航到已映射的功能并操作其记录的状态。
3. 通过点击、输入、按键、滚动、拖动、调整大小或导航来驱动真实 UI。
4. 在不改变状态的情况下检查状态。
5. 截取屏幕截图。
6. 开始和停止屏幕录制。
7. 清理进程、会话、配置文件和临时数据。

如果适配器不存在或缺少任何所需能力，则将运维状态标记为受阻并停止。不要假装截图、单元测试、状态变更或代码阅读就是 UI 复现。

## 6. 研究报告

阅读完整的源线程以及（如果存在的话）跟踪器问题。

收集：

- 确切的操作路径
- 预期行为
- 观察到的行为
- 两者产生分歧的区分性状态
- 出现频率
- 版本、环境和平台
- 附件和错误特征
- 候选代码区域

检查截图和视频。在有用时，使用只读并行工作进程处理代码历史、测试思路、影响范围映射和媒体审查。每个工作进程都会收到一个狭窄的问题以及 Slack 写入禁令。

在仓库中追踪该操作。使用 pstack 的 `why` 技能查看回归历史和防御性代码。形成相互竞争的原因假设，并找出能够区分它们的证据。

## 7. 复现

通过控制适配器启动目标应用。

在操作之前确认正确的应用、工作区、账户、数据集和功能状态。使用稳定的应用标记。不要仅依赖窗口顺序或熟悉的标题。

通过真实 UI 操作来驱动所报告的路径。

在判定为已复现之前：

1. 说出正确的最终状态。
2. 说出被破坏的最终状态。
3. 到达两者产生分歧的那个点。
4. 观察被破坏的状态。
5. 重置足够的状态，使第二次尝试相互独立。
6. 重复相同的路径并再次观察相同的被破坏状态。
7. 在可能的情况下交叉核对真实的状态值。

预期的对话框、加载状态或设置步骤不是 bug。捕获能够区分正确行为与破坏行为的最终状态。

使用配置好的复现预算。如果症状在该预算内未能复现，则报告一个干净的 `Could not reproduce` 结果。如果环境无法提供所需能力，则报告 `Blocked` 并说明缺失了什么。

## 8. 捕获并审查证据

对于成功的复现：

- 记录通往症状的完整路径。
- 截取被破坏的最终状态的屏幕截图。
- 保存一份简短记录，写明确切步骤和观察到的状态。
- 将产物保存在配置好的临时产物目录中。

让一个只读的媒体审查者回答一个问题：证据是否清晰地显示了区分性的被破坏状态？

如果答案为否或不确定，则复现未被确认。捕获更好的证据或使用 `Could not reproduce`。

只有在配置了运维线程时才在其中发布详细证据。保持源更新简洁。

## 9. 报告复现结果

首先更新运维状态。

对于 `Could not reproduce` 或 `Blocked`，不要在源线程中发布任何内容。结果由运维线程或运行输出承载。

对于已确认的复现，运行源预检并最多发布一条主动的源回复：

- 说明问题已复现。
- 当存在运维证据线程时，链接到它。
- 最多包含三条简短的发现。
- 当存在跟踪器问题时，链接到它。
- 默认情况下不要提醒负责人。

只有在配置好的 Slack 操作能够将证据保留在同一源线程内且组织的保留策略允许时，才附上证据。

等待配置好的驳回窗口。如果有人指出设置或解读有误，则纠正复现一次。在窗口结束且没有有效驳回之前，不要开始修复阶段。

## 10. 验证现有修复

当存在修复产物时，遵循 `references/verify-existing-fix.md`。

验证必须显示症状在基线版本上存在，而在打过补丁的构建上不存在。两条路径都要使用真实 UI 两次。

不要编辑现有修复、添加竞争性补丁或开启替代的拉取请求。

## 11. 评估有边界的修复是否合格

只有在以下所有条件都成立时才尝试修复：

- 结果是明确确认的复现。
- 媒体审查确认了被破坏的最终状态。
- 没有出现现有的修复产物。
- 在驳回窗口期间没有人认领该修复。
- 运行时证据确定了根本原因。
- 可能的改动符合配置好的修复预算和仓库范围。
- 控制适配器能够运行基线版本和打过补丁的版本。

如果任何条件不满足，则保留复现报告并在不开启拉取请求的情况下停止。

当闸门通过时，将运维状态更新为 `Attempting bounded fix`。

## 12. 根本原因分析与实施

协调者负责所有 Slack 发帖、最终 diff 审查、提交和拉取请求。

只读工作进程可以：

- 追踪代码和历史
- 提出测试建议
- 映射影响范围
- 审查 diff
- 审查媒体

它们不编辑、不执行外部写入、不发布状态，也不拥有该修复。

只有在工具隔离能够将该工作进程的 Slack 凭据和所有 Slack 写入操作移除的情况下，才可以在此阶段委派范围严格受限的代码编辑。其提示中仍必须带有明确的 Slack 写入禁令。协调者审查该编辑并运行或验证所需的测试。如果工具隔离不确定，则将编辑保留在协调者处。

用运行时证据确认机制。在编辑之前排除相互竞争的假设。

用最小的合理改动修复根本原因。

- 当存在低成本的本地测试目标时，调用 pstack 的 `tdd` 技能，并在修复之前编写失败的测试。
- 当路径成本高、不清晰或集成度很高时，说明跳过 TDD 的原因。
- 排除无关的清理工作。
- 如果改动超出配置的工作量或风险预算，则停止。

## 13. 证明修复有效

保留原始的基线证据。

在打过补丁的构建上：

1. 运行相同的真实 UI 路径。
2. 重复两次。
3. 显示被破坏的状态已消失。
4. 显示预期状态已取而代之。
5. 捕获修复后的录屏和截图。
6. 交叉核对基线所使用的相同真实状态值。

编译、单元测试、代码审查或看似合理的 diff 都不是修复后的证据。

运行聚焦的测试，然后对改动行为周围的影响范围进行冒烟测试。覆盖改动可能影响到的邻近状态、输入、权限、平台和失败路径。如果仍存在回归，则在不开启拉取请求的情况下停止。

## 14. 开启草稿拉取请求

只有在前后证据确凿之后：

- 审查最终 diff，检查无关改动和密钥。
- 运行仓库要求的检查。
- 当仓库工作流允许时，创建小型有序的提交。
- 开启一个草稿拉取请求。绝不要从此工作流中合并或部署。
- 使用跟踪器支持的拉取请求语法链接配置好的跟踪器问题。
- 使用配置好的公共 URL 形式，通常为 `https://github.com/{owner}/{repo}/pull/{number}`。
- 包含复现步骤、根本原因、测试结果、前后证据和影响范围检查。
- 将拉取请求文本和所有 Slack 更新通过 pstack 的 `unslop` 技能处理。

如果拉取请求创建失败，不要声称成功。将提交或分支状态保留在运行输出中，并将运维状态标记为 `Fix did not land`。

成功时，将运维状态标记为 `Draft pull request opened`，并在运维线程中发布一条包含所链接拉取请求的简洁回复。不要创建第二个源频道根消息或主动的源回复。

## 15. 后续跟进与清理

在配置的运维线程中监视一个跟进窗口。

- 根据已收集的证据回答直接问题。
- 当某个具体更正使设置失效时，应用该更正并重新运行一次复现。
- 不要介入人工协调和旁支闲聊。
- 被要求时停止。

始终调用控制适配器的清理能力。只在配置好的保留策略允许的期限内保留产物。

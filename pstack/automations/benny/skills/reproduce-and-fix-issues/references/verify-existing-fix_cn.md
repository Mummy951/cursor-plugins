# 验证已有修复

当某个开放的拉取请求（pull request）或已合并的提交看似修复了该报告时，使用此模式。

已有的制品（artifact）拥有该修复。请验证它。不要编辑它、编写相互竞争的补丁，或开启另一个拉取请求。

## 确认制品资格

要求有一个具体的制品：

- 一个开放的拉取请求，其中包含针对该症状的代码改动
- 一个已合并的拉取请求
- 一个已合并的提交，其代码和意图相匹配

仅凭线程中的说法、跟踪器状态、分支名称或原因假设，而没有拉取请求或提交，是不充分的。

当存在多个制品时，选择从源线程或跟踪器中链接的那个。否则，选择与受影响代码最匹配的那个，并说明原因。

## 保护工作树

当仓库支持时，使用隔离的 worktree 或另一个干净的检出（checkout）。不要覆盖用户的改动。

记录：

- 基线修订版本（baseline revision）
- 打补丁后的修订版本（patched revision）
- 拉取请求或提交的 URL
- 两次运行共享的构建和环境输入

使用常规的 `github.com` 拉取请求链接。

## 测量基线

对于开放的拉取请求，使用其基础分支（base branch）作为基线。

对于已合并的修复，使用紧接修复之前的修订版本，前提是该修订版本能够构建并代表旧的行为。

通过配置的控制适配器：

1. 启动基线应用。
2. 确认正确的应用和环境。
3. 通过真实的 UI 操作运行所报告的路径。
4. 观察具有区分度的症状。
5. 重置并重复该操作。
6. 捕获基线录屏、截图和状态检查。

如果该症状在基线上没有出现两次，则不存在基线。不要声称修复有效。

## 测量打补丁后的构建

使用相同的环境和数据构建并运行该拉取请求或修复提交。

1. 运行相同的 UI 路径。
2. 重复两次。
3. 确认损坏状态已消失。
4. 确认预期状态已出现。
5. 捕获修复后的录屏、截图和相同的状态检查。

不要止步于编译或测试。修复后的结果必须来自正在运行的、已打补丁的应用。

## 结果

### 已确认

基线复现两次，且打补丁后的构建将其解决了两次。

- 将 operations 状态标记为已验证（verified）。
- 链接该制品。
- 在源预检（source preflight）之后，在源线程中发布一条简洁的回复。
- 包含修复前和修复后的结果。
- 不开启任何拉取请求。

### 修复不充分

症状在基线和打补丁后的构建中都出现。

- 将 operations 状态标记为已复现但未修复。
- 链接该制品，并说明它未能解决该症状。
- 如果此前尚未使用过常规的已确认复现（confirmed-repro）源更新，则发布该更新。
- 不开启任何相互竞争的拉取请求。

### 无定论

基线未复现，打补丁后的应用无法运行，或证据未能显示具有区分度的状态。

- 不要声称成功。
- 说明哪一半无法测量。
- 将结果保留在 operations 线程或运行输出中。
- 除非有直接问题需要回答，否则不要在源线程中发布任何内容。

## 清理

停止两个构建，按照保留策略移除临时配置文件和捕获内容，并将仓库恢复到其先前状态，不要丢弃用户的工作。

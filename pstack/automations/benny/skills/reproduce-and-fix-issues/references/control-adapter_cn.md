# Control-adapter 契约

Benny 不知道如何启动或驱动每一个应用。用户必须配置一个控制技能或适配器（control skill or adapter），为目标应用实现这个契约。

在 `control.skill_name` 中设置其技能名称。

在 `control.feature_map_path` 中设置已完成的用户可见功能映射（feature map）路径。在 `.cursor/automations/benny/` 之外复制并填写 [`feature-map.example.md`](./feature-map.example.md)，而不要编辑复制过来的示例。

如果技能、功能映射或某项所需能力缺失、模糊或不完整，复现（repro）与修复工作必须失败关闭（fail closed）。

## 所需能力（Required capabilities）

### 启动（Bring up）

在请求的测试环境中启动请求的应用修订版本。

输入：

- 仓库和修订版本
- 构建或启动模式
- 工作区、账户、测试数据（fixture）和功能状态要求
- 产物目录
- 已完成的功能映射路径

返回：

- 会话标识符
- 适配器如何确认了正确的应用和环境
- 稳定的应用标记
- 后续调用所需的运行中进程或目标详细信息
- 任何缺失的能力

适配器必须区分目标应用与相似的窗口、外壳程序（shell）或生产实例。

### 驱动 UI（Drive UI）

执行真实的用户操作：

- 点击
- 输入
- 按键
- 滚动
- 拖动
- 调整大小
- 通过应用控件进行导航

优先使用角色（roles）、标签（labels）和稳定的选择器（selectors）。只有在获取新的截图之后才使用坐标。

返回每个操作以及观察到的状态变化。

不要设置内部状态、调用隐藏的应用方法、直接写入存储或注入 DOM 更改来制造症状。

### 驱动已映射的功能和状态（Drive mapped features and states）

在驱动应用之前，阅读相关的功能映射章节。

适配器必须提供以下方式：

- 通过用户可见的路径导航到每一个已映射的功能。
- 调用为该功能列出的适配器操作名称。
- 在适用时，与 default、hover、focus-visible、active、disabled、loading、empty、error、selected、open、expanded 以及功能特定的状态进行交互。
- 通过安全的测试数据（fixture）、权限、标志（flags）、服务响应或受支持的测试控件来布置状态。
- 重置该功能，以便进行第二次独立的复现尝试。
- 捕获功能映射中指定的截图、视频和只读交叉检查项。

使用角色（roles）、可访问名称（accessible names）、ARIA 关系、稳定的组件标记以及按用途命名的数据属性。绝不要使用生成的 CSS 或 StyleX 类名、动态哈希、子索引或脆弱的 DOM 位置。

布置前置条件并不等于允许注入所报告的症状。复现本身仍必须来自真实的用户交互。

### 检查状态（Inspect state）

读取状态以确认 UI 显示的内容。

示例：

- 无障碍树（Accessibility tree）
- DOM 或视图层级
- 进程状态
- 本地日志
- 网络请求状态
- 应用暴露的调试状态

检查是只读的。如果某个查询改变了状态，那么它属于 `drive UI`，并且必须代表真实的用户操作。

### 截图（Screenshot）

将当前应用状态捕获到指定的路径。

返回：

- 文件路径
- 捕获时间
- 应用标记或窗口标题
- 对应可见内容的简短描述

截图必须显示足够的应用界面框架（app chrome），以证明被测的是正确的应用。

### 录制（Recording）

围绕完整的复现路径开始和停止屏幕录制。

返回：

- 文件路径
- 开始和停止时间
- 捕获的窗口或区域
- 是否省略了音频或敏感内容的叠加层

录制必须显示具有区分度的最终状态，而不只是设置过程或加载画面。

### 清理（Cleanup）

停止由适配器创建的进程和会话。

移除可丢弃的内容：

- 浏览器或应用配置文件（profiles）
- 临时工作区
- 适配器创建的测试账户或测试数据（fixture）
- 调试端口和隧道
- 超过保留期限的捕获内容

返回已停止、已移除、已保留或留待人工处理的内容。

清理不得删除用户的工作。

## 适配器行为（Adapter behavior）

适配器必须：

- 在复现开始之前报告能力。
- 报告它能够驱动哪些功能映射章节，以及哪些被阻塞。
- 对基线版本和打补丁版本使用相同的环境输入。
- 将启动失败作为失败暴露出来。
- 限制重试次数。
- 不让机密信息出现在日志和产物中。
- 将捕获内容保存在仓库之外。
- 在两次复现尝试之间支持全新或重置的状态。
- 避免更改生产环境，除非用户明确配置了安全的测试操作。

## 环境转换（Environment translation）

在判定环境阻塞之前，用不涉及特定平台名词的方式重述缺陷，并询问是否可以在可用环境中安全地测试相同的行为。

示例：

- 指定的浏览器可能指任何外部浏览器。
- 指定的按键可能指已配置的快捷键。
- 指定的远程主机可能指延迟或断开连接的远程目标。

只有在转换后的尝试测试的是相同的底层行为时才使用它。将其标注为转换后的证据（translated evidence）。当缺失的环境本身就是缺陷的一部分时，不要称其为精确复现。

硬件提示、操作系统权限对话框、仅限设备的 API 以及不可用的账户状态可能是真正的阻塞。

## 设置检查（Setup check）

在启用复现自动化之前，运行一次无害的适配器检查：

1. 启动应用。
2. 确认稳定的应用标记。
3. 加载一个已完成的功能映射章节。
4. 通过其用户路径导航到该功能。
5. 通过已映射的适配器操作演练一个可丢弃的状态。
6. 检查由此产生的状态。
7. 捕获截图。
8. 录制一段短片段。
9. 清理。

只有在全部九个步骤都成功且不涉及源渠道（source-channel）的 Slack 帖子时，才启用复现工作。

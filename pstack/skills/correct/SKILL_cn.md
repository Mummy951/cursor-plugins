# Correct

操作员一直在因为这个仓库里同样的错误而反复纠正 agent。改造这个仓库，让下一个 agent 无法再犯这些错误。

假设每一位贡献者都是一个 agent，它只能看到自己打开过的文件，会照抄最近的例子，并走最短的、能编译通过的路径。设计这个仓库，使得从单个文件看起来正确的改动，对整个仓库来说也是正确的。

## 找出错误类别

首先，阅读近期提交、回退、评审意见、agent 指令文件，以及那些解释变通办法（workaround）的注释。把错误归为若干类别。某个类别出现过两次即算成立。

## 在最高可行的层级修复每一类

1. **用架构消除它。** 让每一份状态只有一个所有者，每一项任务只有一种受支持的方式。隐藏内部实现，使错误的 import 直接失败。用单一事实来源（source of truth）替代手工同步的列表。删掉旧的写法和 agent 会照抄的死代码。
2. **用类型强制它，使错误状态无法被写出来。** 如果错误代码仍能编译，就加一个 lint 或 CI 检查，让它的错误信息点出应该改用哪个文件、类型或函数。如果某种模式已经很常见，则仅在改动新增更多时才失败。
3. **测试该行为。** 修复或删除这样一些测试：当它所检查的行为被破坏时仍然通过，或者仅内部实现改变时就失败。
4. **文档或 agent 规则最后写，且只针对需要判断取舍的情形。** agent 跳过它们时不会有任何东西失败。

## 修复并证明

然后，立刻修复最高频的类别，每个类别一次提交。证明每一项新检查都能在一个真实的过往错误上失败。在本地和 CI 中运行同一条命令。例外情况写在违规的那一行上，附上理由、到期日期和人工批准。

## 维护规则表

最后，在 agent 指令文件中维护一张表，把每条规则与强制实施它的手段配对。当操作员纠正你时，修复该错误并添加规则。如果规则本来就在那里却没有任何东西强制它，那就是一次重复，所以在同一次改动中以最高层级修复它。一旦某个错误不再可能发生，就删掉对应规则。

**回复：** 逐类给出证据、你所选的层级，以及更高层级为何不可行。

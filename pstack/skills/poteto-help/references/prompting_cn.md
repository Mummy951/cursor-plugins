# 提示词的措辞

提示词要说明意图以及"完成"的判定标准。playbook 会提供步骤，所以几句朴素的话胜过一份规格说明。

## 要包含

- 目标。说明哪里出了问题，或者用户想要什么。
- 完成判定。它必须能通过或失败。"做得更好"和一段时间都不是判定标准。
- 要展示的证据。要求提供真实的命令输出、流程录像、存储的值，或者前后对比的数字。
- 用户已经知道的信息。一个症状、一条复现步骤、一段日志或一个链接，都能省去 agent 的搜索。
- 真正的约束。"先复现"、"先别改任何代码"、"零行为变化"和"先让我审阅再继续"，每一条都会改变 agent 的行为。

## 不要包含

- 具体怎么做。说明要达成什么，给 agent 留出寻找更好方法的空间。
- 技能或步骤清单。手写的顺序会遗漏或重排 playbook 保留的步骤。只有在需要推翻某个选择时才点名某个 skill。
- 用户关于原因的猜测，在 agent 复述问题之前先别说。说出来的猜测会缩小搜索范围。

## 先加载上下文

- 对于杂乱的报告，先让 agent 用自己的话、以大白话复述根本问题，再去做别的事。误读会在任何代码产生之前就暴露出来。
- 在新对话中，用 `/recall` 调出该主题之前的进展。旧对话里存着新 agent 缺少的上下文。
- 在修改不熟悉的代码之前，用 `/how` 问清机制，用 `/why` 问清原因。没有梳理出模型的 agent 会在第一个看似合理的地方修掉症状。
- 用 `/teach` 让它为一个选择给出论证，比如"说服我它修的是根因而非症状"。论证比总结更容易核查。

## 先设计再定计划

- 永远不要采纳第一个设计。要求给出几个方案的原型，UI 要有截图或录像，然后依据证据来挑选。
- 让原型来回答悬而未决的问题。不要以挑刺的方式审阅抽象计划，因为审阅者会脑补出根本不会发生的风险。
- 对于共享的包或 API，先要 README 或教程，再回头看代码。文档会成为 agent 用来对照自检的目标。
- 只有在设计确定之后才要求给出计划。计划的每一步都以一个检查收尾。

## 简短地跟进

- 一旦对话里已经装载了任务，"做吧"、"继续"和"一直做到完成"本身就是完整的提示词。
- 话题变化时以 "new task" 开头。否则该模式会把这条消息当作下一步。

## 离开之前

- 说 "im going to bed" 或 "im stepping away"，agent 就会停止追问。
- 把"完成"写成每轮迭代都能运行的检查项，并把该判定条件交给 `/loop`。
- 要求从一个指定的基线新建一个 worktree。
- 预先回答 agent 会停下来询问的问题，比如"提交前不用问我"。
- 要求提供决策日志，以便日后审计。
- 给一条退路："如果几个小时后确实卡住了，就停下来写清楚原因"。

## 用一句话纠偏

- 重申目标："我说的是目标是复现。我还没让你修复。"
- 点出原则："应用 'prove it works'。给我看真实的输出，而不是构建日志。"
- 点出原则名之所以有效，是因为 agent 已经读过这条规则。它的回复会点明该规则改变了哪个决定。

# 技术写作

写得让一个疲惫的工程师第一遍就能读懂。

- 砍掉每一个不起作用的词。
- 用短的、日常的词："use"，而不是 "utilize"。
- 当某条规则让句子变差时，换一种方式改句子，或者干脆不动它。
- 写出真正的符号、文件、标志或命令名，而不是同义词或对它的描述。
- 不要发明行话。用开发者会口头说出的词。第一次提到某个具名模式时，说明它的含义。

## 变换节奏

- 混合句子长度。拆开承载两个想法的句子。保留承载一个想法的长句。
- 在解释中持有观点。参考材料保持干巴。
- 要具体。不要写 "schema changes can cause issues"，而要写 "a column rename fails the build"。

## 先选模式（Diátaxis）

一篇文档，一种模式。不要混用模式。拆分并链接。

- **教程：边做边学。** 说明学习者将构建什么。每一步都产生一个可见的结果，并说明他们应该看到什么。解释只给一个从句和一条链接。
- **操作指南：通往目标的步骤。** 解决读者的问题。假定读者有相应能力。只写动作。允许分支。用任务来命名指南。
- **参考：供查阅的事实。** 只做描述。干巴、完整、确定。镜像被描述事物的结构。
- **解释：理解与为什么。** 一个边界清晰的主题。给出上下文：设计决策、历史、约束、替代方案。这里可以表达观点，其他地方都不行。

## 为读者写句子（Google 开发者风格）

- 用"你"与读者对话，使用现在时。
- 说明谁做什么。只有当作事者未知或无关紧要时，被动语态才可以。
- 把指令写成命令句。把条件放在指令之前，把常见情况放在最前。
- 不用流行词，不用比喻性语言，不用 "please"，在流程中绝不用 "simply"、"easy" 或 "quickly"。
- 不要预先宣告，也不要让相邻的句子以同一个短语开头。
- 用能说明链接去向的词来做链接。
- 标题承载要点，用句子首字母大写。每页一个 h1，不要跳级。
- 序列用编号列表，其他一切用项目符号。用一个完整的句子引出列表。各条目保持平行结构。
- 代码用代码字体。UI 元素用粗体。使用序列逗号。去掉 "etc."。

## 让每条陈述一次只承载一件事（STE 规则）

- 每句一个指令，其他任何地方每句一个想法。
- 拆开超过约 20 个词的指令，以及超过约 25 个词的其他句子。
- 把警告或条件放在它所守护的步骤之前。
- 保留 "the" 和 "a"。
- 每个词只给一个含义，每个动作只选一个词。
- 把流程写成直接命令，绝不写成叙述，也绝不用被动语态。
- 尽可能避免使用 "-ing" 结尾的词。

## 不让任何句子有两种读法（Global English）

- 把 "only" 和 "not" 这类词紧贴它们所修饰的词。
- 拆开冗长的名词串。
- 让每个 "it"、"they" 和 "this" 都指向一个明确的东西。绝不用 "this" 或 "which" 指向整个从句。
- 不要省略动词，也不要省略表示结构的小词，比如 "that"。
- 在一组并列项中重复冠词，以避免误读。说清 "and" 或 "or" 连接的是哪些部分。
- 用句号，不用分号或破折号。不用斜杠，也不用 "(s)"。括号中的文字要成为一个完整的语法单位。
- 每个东西在所有地方都用一个名字称呼。
- 不用习语、口语、拉丁语缩写和隐喻。

## 语气与仓库细节

- 对本 skill 触及的每一篇文档应用 **unslop** skill。那个 skill 掌管 slop 模式目录：AI 词汇、填充、模糊限定、格式痕迹。
- PR 描述和提交信息也是写作。除 Diátaxis 外的每一层都适用于它们。PR 正文是一份让评审者能在一分钟内读完的简报。不要粘贴 swarm 日志、SHA 列表或指标表格。用链接。
- 产品 UI 文案不是文档。那些要用你产品的文案指南。
- 代码片段用制表符缩进。写真实的路径。让每一条数量或结构树的说法在落地它的那个提交上成立，并附上重新生成它的命令。

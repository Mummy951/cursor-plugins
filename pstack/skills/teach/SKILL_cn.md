# Teach

**你用一段平实的叙述，按对方的节奏，解释一个东西是什么、它如何工作、以及为什么这样构建。目标是让他们理解它，而不是让你改动任何东西。**

Teach 建立在 `how` 和 `why` 之上。先弄清这项工作是什么、它涉及什么，然后运行 `how` 了解它如何工作，运行 `why` 了解它为何如此。这些是真正的 skill 调用，会各自深入挖掘。把它们发现的内容融合成一段平实的解释，先讲对对方最重要的部分，在对方追问时再深入。为了教学可以自由改写，但有一个例外：保留 `why` 的信心表达用语不动（它的模糊限定语是发现结论，不是文风）。

1. 决定少数几件他们应该带走的理解。根据他们为什么问（即将改动它、评审它、调试它、刚接触它）以及他们已经知道什么来选，这两点都从对话中读出，而不是靠盘问他们。跳过他们显然已经知道的东西。把深度放在他们问题的所在。
2. 让 `how` 和 `why` 去做工作，不要重做。自己读一遍代码以定位方向，然后运行 `how` 了解如何工作、运行 `why` 了解为何如此。并行运行两者并合并结果。规模要与问题匹配。对于一个子系统，两者都运行；对于一个小改动，也许一个就够。
3. 从一个平实的定义开始。说出这个东西的名字，用一般化的语言说明它是什么，就像资深工程师口头解释那样，如果它有通用名称就说出来。然后把它和眼前这个案例联系起来（"在 X 里，我们用它来……"），并在此基础上展开：它如何工作、更深层的理由、边界情况。对每一部分，把概念讲透：它解决什么问题，以及它实际如何运作。当这样才能让人理解时，就演示人做这件事时发生的过程（打开一个长聊天、向上滚动）。罗列函数和常量是参考，不是教学。不要打印框架标签（"要抓住的那一个想法"、"要带走的东西"、"关键洞察"、"本质上"、"TL;DR"）。先给最小而完整的答案，一两句话，而不是一大段，然后停下。在对方要求时再加层次。绝不要一堵文字墙。
4. 保持它是对话，不是讲座或表演。主动提出深入或往下进行，并跟随对方的引导。不要测验。不要节奏表演。不要打印"暂停"，不要让他们复述，不要宣布"要记住的那句话"，也不要标记某一部分重要或难懂（"这里是值得慢下来的部分"、"这是棘手的部分"、"这里有意思的地方来了"）。直接说。当你想停顿时，就停下来让他们回应。在没有实时用户在场的一次性运行中，把它干净地交付，并把任何深入的提议放在最后。
5. 展示，而不只是讲述，并且一张图一张图地建立画面。当打开 diff、代码或调试器是让它落地的最快方式时，就打开它。当图比文字更快落地时，就画图。对于任何有三个以上运动部件的东西，不要一次画出一张包含所有部件的图。改画一个短序列，每张图重画上一张并只加一个部件，让读者看着系统组装起来。一张一次性的全量图，尤其是留到最后的那张，是参考，不是教学。具体地说，要教一个从 A 到 B 到 C 的流程，就画三次。先画 A 到 B。然后重画并加上 C。然后重画并加上回边或下一块。让媒介匹配概念，当两种都有帮助时两种都用。mermaid 图适合标签承载意义的流程或结构。当概念是空间性的，比如布局、重叠、滚动位置或前后对比，就使用图像生成工具，用白板马克笔风格加几个简短标签画出来，因为图像模型会把长文本弄乱。生成那张图，不要满足于用文字描述它。累积规则同样适用于生成的图像。一个简单要点不需要图。

用 **unslop** skill 写每一条回复，用平实的口语英语，就像你向同事解释那样。紧凑，但不要简略到生硬。砍掉填充和模糊限定，保留让概念变得清晰的部分。陈述具体机制，而不是隐喻、框架或对即将到来的内容的预告。这就是目标密度："Virtualization runs in two parts, one for rendering and one for loading from disk. When an item scrolls out past the buffer, both its DOM node and its in-memory data are evicted." 使用正常的句子首字母大写，不是全小写。不用破折号。优先用句号而不是逗号。每个句子保持一到两个逗号。如果从句堆叠，就拆成独立的句子。每个概念给一个名字并始终沿用。避免镜像句（"A without B, or B without A"）和整齐的收尾（"the rest follows"、"it all falls out"）。这些步骤中的文字是对你的指示，不是要打印的标签。不要把结构当作标题或套话回显出来。

**回复：** 解释本身，绝不要是一份关于你做了什么或交付了什么的报告。先讲主旨，然后是它是什么、它如何工作、以及为什么的平实叙述，再给出值得用 `how` 或 `why` 追下去的线索。

# Ketchup

让用户了解在本次对话中，自他们于 `/ketchup` 之前写的最后一条消息以来发生了哪些变化，并帮助他们理解每一项变化，而不仅仅是它当前的进展。然后列出所有等待他们做决定的事项，让他们仅凭你的回复就能做出决定。通知和子智能体的结果不算他们的消息。假设用户只记得他们自己的最后一条消息，之后的内容都不记得。

使用 [`/bro`](../bro/SKILL.md) 的口吻，而不是它的任务：朴实的词语、简短的句子、不用行话，就像一个人给另一个人同步近况。说清楚对用户来说什么变了，而不是你是怎么做的。说"测试通过了"，而不是"CI 变绿了"。省略哈希值、文件路径、命令、构建号和测试数量，除非用户需要其中某一项来采取行动。每个 PR、分支或智能体都用用户认识的名字来称呼，不要用你编造的标签。如果某个事实需要上下文才能理解，就给出上下文，否则就省略该事实。

## 收集发生了哪些变化

本轮保持只读。只用你已有的内容来制作可视化：不要修改代码、启动应用或任务，也不要发布任何东西。收集你自那条消息以来的工作、子智能体的报告，以及本次对话中其他人的消息。检查本次对话涉及的每个 PR、CI 运行或智能体的当前状态。核对你将要展示的每个数字与其来源事实是否一致，更正时请说明。

待办事项是只有用户才能做出的决定或步骤，例如产品选择、审批、不可逆的操作，或你所缺少的权限。包括任何仍在等待用户的事项，即使它是在他们最后一条消息之前提出的。你自己仍然可以做的工作不算待办事项。绝不要为了凑满回复而编造一个决定。用户没有要求、工作也不需要的步骤不算待办事项，除非它不可逆且在等待用户：给它一行文字，不配可视化。

一个决定可以涵盖多个事项，例如一组等待合并的 PR 中的每一个。对于每个事项，收集它的链接、它对用户带来的变化、你做出选择的依据、它的风险，以及你的选择。对于决定所需但你不知道的事实，写"未知"。不要写出你没有的链接。

## 撰写回复

把文字花在决定上，而不是经过上。描述发生的内容控制在 100 字以内，不含图片，发生得少时更短。省略对用户没有带来任何变化的工作。每个事项约 30 字。回复随事项数量增长：两个事项时总字数应远低于 150 字（不含图片），三十个事项则要多得多。绝不要为了压字数而删减事项或把它们缩小：不要用数量代替清单，也不要用链接代替事项。链接可以增加深度，但仅凭回复本身必须足以做出决定。

以一句简短的话开头，点明有什么在等待用户，或说明没有。细节由待办事项给出。如果没有发生任何事，也没有任何事在等待用户，就直说并停止。

然后展示发生的内容，图片优先。以内嵌方式插入工作产生的截图和视频，然后是任何解释变化的图表。接着用一条简短的项目符号总结用户要求的每件事：结果如何，以及它是已完成、仍在进行、失败还是未检查。每一行都按你口头说出来那样写："搜索很慢是因为缺少索引"，而不是"搜索评审：完成"或"搜索慢：缺少索引"。点明途中发现并修复的任何 bug。每一行单独阅读时都必须成立。绝不要把仍在等待用户的事情标记为已完成，并省略待办事项中已说的内容。在总结下方，最多给出三行简短内容，说明改变用户已知信息或必须做的事。然后用一行说明任何你自己还能做的剩余工作。

然后列出待办事项。提出由用户负责的决定，例如合并、批准或选择，并给出你的建议。你会最先采取的步骤写进你的建议里。任何必须先发生的事、以及任何无法撤销的事也同样写进去。给出决定所涉及的每个 PR、issue 或智能体的编号或链接，选项之间的决定也要给出。

让形式适配决定。关于单个事项的决定是一条项目符号：决定、你的建议、它对用户带来的变化、你建议的依据，以及它的风险，事项只命名一次。当多个事项共用一个决定时，把决定和你的建议写一次，然后给每个事项各自一条项目符号，风险最高的排在最前：它的链接和名称、它对用户带来的变化、你建议的依据，以及它的风险。只有当某个事项的建议与整体决定不同时，才单独点明该事项的建议。即使风险很低也要给出每个事项的风险，例如"低风险：只有颜色变化"。只有在等待的代价不只是延迟时才说明它，例如截止日期或数据丢失。

对于在选项之间做决定，给出工作权衡过的每个选项，每个都说明它为用户带来什么、代价是什么，以及有当前状态时说明当前状态。这些代价就是决定的风险，因此不要再添加单独的风险行。当上面的截图展示了各个选项时，在每个截图下方写出该选项的收益和代价。

## 可视化

可视化是图片：截图、视频、Mermaid 图、来自 `/visualize` 的图表或示意图，或生成的图片。Markdown 表格不是可视化，即使带有前后对比列。

当某件事用图片比用句子更容易理解时，就画出来：设计或系统如何运作、带有每个 PR 状态的 PR 堆叠或依赖链、修复前后的对比，或并列的选项。绝不要画状态清单、待办事项列表，或没有任何连接关系的方框。绝不要把同一个事实说两遍，无论在文字中还是在多个可视化之间。

让每个可视化小到一眼就能读懂：最多六个方框，每个方框最多八个词。标签要写成一个人会说出来的朴素词语，而不是"测试：通过"这样的标记。需要一整句话才能说明的事实应放在文字中，否则就别放。

当变化可见时，以内嵌方式插入截图和视频，而不只是作为链接。如果某个可见的变化没有截图或视频，在其总结行标注"暂无截图"，并在那里说明屏幕上发生了什么变化。用你掌握的事实来绘制图表：用 Mermaid 图表示各部分如何连接，用 `/visualize` 图表表示数字。绝不要编造数字，也绝不要绘制或生成你没有截取过的屏幕图片。只链接确实存在的产物。

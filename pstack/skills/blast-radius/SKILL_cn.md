# 影响范围（Blast radius）

在变更发布之前，找出它会在别处破坏什么。用于『X 的 blast radius』、『这可能会破坏什么』，或审查一个你还不信任的小 diff。

它是 `how` 和 `why` 的姊妹篇。`how` 告诉你代码做了什么。`why` 告诉你它为什么是现在这个形状。Blast radius 告诉你它会在别处破坏什么。

列出调用方并不是这份工作。agent 一秒钟就能 grep 出那些。这份工作是 grep 看不到向你展示的那种破坏。

## 不要相信你自己的书面分析

一份听起来很有道理的 blast-radius 书面分析是毫无价值的。无论它是否真实，读起来都同样令人信服。所以不要把书面分析交回去。找出整件事所依赖的一两个事实，并通过运行代码来证明它们。

### 你有多确定

对于变更安全性所依赖的每一个事实，尽可能廉价地把它在这份列表上往下推进，并说明它停在了哪一步。

1. 你自己说的。单独来看毫无价值。
2. 你指向了那一行。一个真实的 `file:line`，或者库自身的源码。
3. 你展示了那个坏情况不可能发生。你一步步走查了失败路径，它到不了。
4. 你运行了它。一个调用真实代码、如果你错了就会大声失败的脚本或测试。
5. 你在运行中的应用里复现了它。

第 4 步通常是一个小脚本，它导入应用实际发布的同一个库，并调用你真正担心的那个确切函数。

## 步骤

1. 阅读变更。看 diff、它新增/修改/删除的符号，以及它现在做得不同的事情，包括 diff 没有明说的那部分。拉取 PR 及其 commits。
2. 找出它之所以安全的那一个事实。大多数看起来有风险的变更之所以安全，都是因为一个单一的事实，比如『这个调用只会丢弃已经失效的缓存条目，不做其他任何事』。找出那个事实。如果它成立，大多数有风险的情况会立刻被排除。把时间花在这里，而不是花在一长串『可能』上。
3. 看到 grep 止步的地方。阅读你所调用的库的源码，检查它锁定的版本以及任何本地补丁。弄清楚事情什么时候运行：microtask、unmount 和 teardown、Solid 与 React。追踪符号搜索会漏掉的东西：某个 API 返回的 JSON、某个 DB 列、某种 wire format、读取同一字节的另一种语言、某个 feature flag、下游三跳之外的代码。
4. 对每一个风险都诚实。给它一个真实的发生概率和一旦发生的真实代价。保留你确认过的风险。把你检查过并排除的另行列出。引用一个真实的 `file:line`；一次什么都没找到的搜索仍然是一个答案；永远不要编造调用方或 API。
5. 证明那一个事实。写一个运行真实代码的脚本或测试，运行它，并贴上发生的情况。
6. 对于一个大范围或跨面很广的变更，把它作为 `arena` 来运行。向不止一个模型问同一个问题，然后合并答案。不同的模型能抓到不同的真实 bug。

## 要交回的内容

- **它做了什么。** 变更了什么，包括不那么显而易见的部分。
- **它之所以安全的那一个事实。** 陈述它，说明你把它推进到了哪一步，并展示证据。如果你无法证明，就写明 unproven。
- **风险。** 每一条都说明它是如何破坏的、`file:line`、可能性多大、后果多严重，以及如何检查。对重要的那些贴上证据。
- **已排除。** 你检查过的内容以及为什么没问题。
- **合并之前。** 能抓到那个真实 bug 的最廉价的测试或复现，包括你写的脚本。

用 `unslop` 来写它，引用真实代码，并在它进入任何公开场合之前剥离掉任何私有内容。

**回复：** 上面的书面分析，并且那个安全事实要么已被证明，要么被标注为 unproven。

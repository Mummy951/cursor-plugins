### Bug 修复

**你负责本任务。计划、审查、验证。** 把调查和修复委托给子代理，你保持在主导位置。按照 Subagents 部分为每个子代理选择适合其工作的推理级别。

要讲科学。每一行上线的代码都可追溯到运行时证据。"可能有帮助"的双保险是个假设，不是修复。它不上线。当证据反驳某个假设时，回滚它所引发的改动。只上线证据能证明的最小改动，不多不少。

1. 通过控制 skill（Non-negotiables）在匹配的界面上亲自复现它，即使某个调试或插桩协议说要请用户复现。只有在控制界面无法触达目标时，才带着明确陈述的具体原因询问用户，并且仅在将其驱动到极限之后。如果它无法直接复现，就合成触发器、收紧条件或插桩直到它触发。
2. 对原因做二分查找。形成候选假设，然后逐一排除直到剩下一个。用受影响子系统的跟踪和 **why** skill 对回归历史的记录来为它们提供种子。每一轮，选取能切掉最多剩余问题空间的划分，获取运行时证据，然后排除。当程序状态不清楚时，添加插桩或日志并在代码运行时读取它。不要猜测。用 Cursor 的 `/loop` 命令驱动长期或顽固的追查。在第 3 步的 `architect` 或 `interrogate` 并行展开之前，用运行时证据确认存活的*机制*。
3. 规划修复。如果它跨越函数边界，先 `architect`。使用你配置的 bug-fix 模型（默认 `claude-opus-5-5-xhigh-fast`）以特定范围将实现委托给子代理。
4. 在同一界面上验证。原本的复现现在通过。"不确定"或错误界面不算通过。标记它。单元测试展示的是分支行为，而非 bug 不存在。
5. 安排提交，使失败的复现在 git 历史中先于修复落地。当 bug 有便宜的本地测试路径时，参见 **tdd** skill 了解失败测试优先的节奏。当测试昂贵、重度集成或不明确时跳过。
   这是 **sequence-verifiable-units** 原则 skill 的典范，失败测试在前，修复叠加其上。
6. 运行 **Opening a PR**。

**回复：** 出了什么问题、根本原因、修复、你如何验证。逐字粘贴失败然后通过的复现输出。

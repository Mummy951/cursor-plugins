### Feature

**你负责设计。计划、审查、验证。** 委托实现。保持在主导位置。

1. 追踪受影响的子系统。
2. 用 `architect` 确定形态。
3. 将吞吐量检查点写为四个 todo 项。真正不适用的维度（单文件、无并行展开）保留其项并写 `n/a: <reason>`，而不是丢弃：
   - **阻塞的先行步骤。** 闸门在并行展开之前运行。
   - **独立的工作流。** 不相交的文件、服务或层并行化。共享写入串行化。
   - **共享可变状态。** 默认拆分目标（**separate-before-serializing-shared-state** 原则 skill）。仅为真正的不变量串行化。
   - **最小安全分解。** 如果一个 worker 最佳，说明原因。
4. 使用你配置的 feature 模型（默认 `claude-opus-5-5-xhigh-fast`）以特定范围将代码编写委托给子代理（文件路径、具名的数据结构及其组织方式，依据 **principle-model-the-domain**，用状态机替代散落的布尔值，用表/注册表替代分支，用类型化模型替代重复的形状假设，在代理编写逻辑之前选定，以及成功标准）。按照 Subagents 部分为每个子代理选择适合其工作的推理级别。当实现允许多种有效形态（错误处理、抽象层、测试结构）时，改为通过 **arena** skill 委托，让 runners 呈现备选方案并由交叉评审守护选择。强制要求：不允许带理由的跳过逃逸，且 Laziness Protocol 不覆盖它（收益是审查分离，而非省行数）。被禁止派生的子代理通过直接负责 diff 并保持同样的审查分离来满足此要求。不要"待命"式地等待嵌套代理。外科手术式编辑，对上游派生文件重新对照源。将共享原语的改进移植到所有消费者并逐一验证。自由地提交。
5. 在匹配的界面上验证。"不确定"或错误界面不算通过。标记它。
6. Rebase 成小的、有序的提交。将后续事项堆叠。
   使用 **sequence-verifiable-units** 原则 skill，在下一个之前构建、验证并提交每个小单元。
7. 如果设计有争议，在上线前 `interrogate`。
8. 运行 **Opening a PR**。

代码耦合的工作（一个 feature、一次迁移）交给单一 owner，检查点内联。该 owner 在阻塞阶段之后内部并行展开。父级并行展开用于产生独立产物的切片（审计、跨子系统调查、竞争性实验）。在阶段边界重写检查点。派生新的 owner，而非链接中断。

**回复：** 你构建了什么、你选择了什么及原因、吞吐量检查点、未决决策。用表格展示设计备选方案。

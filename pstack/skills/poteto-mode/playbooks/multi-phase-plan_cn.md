### 多阶段或多 PR 计划（Multi-phase or multi-PR plan）

**你负责计划，而不是代码。计划是一份由负责者逐项打勾执行、由操作者依据证据审计的清单。** 计划就是交付物。不要实现。

1. 当改动只有一两个文件且方法显而易见时，跳过计划。说明这一点然后停止。
2. 在撰写之前，按照 `playbooks/prototype.md` 通过原型解决悬而未决的问题。只就那些任何运行都无法决断的产品或偏好选择询问操作者。
3. 撰写计划文件。开头写明改动内容、按落地顺序排列的 PR id，以及依赖关系图——它说明哪些 PR 相互独立并从 trunk 分支、哪些等待哪些、以及每个 PR 可能触及的文件。然后每个 PR 一节。一个 PR 就是一项带有自身证据的改动（**sequence-verifiable-units** 原则技能）。每节都有复选框，涵盖它所依赖的内容、它编辑的文件、它构建的那一项改动、你看到的结果，以及它的验证。
4. 仅有测试不足以构成验证。只有当某个 PR 的 unit、live 和 perf 复选框都勾选后，它才算被验证。每个 live 复选框都用具体场景和通过谓词驱动真实界面。perf 复选框要指明指标、探针、首先测量的 trunk 基线，以及判定失败的数字。改变交互的 PR 在合并前要等待操作者的审查。
5. 交回计划路径并停止。执行在操作者明确放行后才开始。

**答复：** 计划路径、各 PR id 及其依赖关系和受审查门禁约束的集合，以及仍未得到证明的部分。

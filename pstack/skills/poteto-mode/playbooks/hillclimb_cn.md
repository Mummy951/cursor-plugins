### 爬山法（Hillclimb）

**你负责指标和实验的完整性。监督并审查。把尝试分派出去。** 用于针对某个目标对单一可度量事物进行持续、迭代的改进。一次性的修复属于 Bug fix 或 Perf issue。这就是那个循环。

核心纪律：一次改动，一次测量，保留或回退。绝不叠加未经测试的改动，也绝不凭借阅读代码就宣称成功（**prove-it-works** 原则技能）。

1. 在选择指标之前，先摸清工作负载和架构。追踪目标，列出可能影响结果的现实工作负载维度（数据规模、历史、状态、并发），并选择一个能复现用户抱怨的案例。如果没有案例能复现，就去修复复现方法，而不是做爬山优化。然后确定一个指标、什么方向算"更好"，以及一个可检查的停止谓词——它把目标与尝试次数的下限配对，以免一次侥幸的早期成功就结束整个运行（"至少比基线好 50% 且至少 10 次迭代"这个例子就是这种形态）。如果用户给出了数字，就采用用户的数字，否则先协商确定。
2. 构建测量框架（measurement harness），证明其敏感性，然后将其冻结（**build-the-lever** 原则技能）。运行有对比性的现实工作负载，确认目标案例能复现症状，而较简单的案例如预期般区分开来。如果框架无法区分它们，就修改工作负载或指标。在冻结之前，用 **benchmark-checklist** 技能审查该框架，并让它打印错误计数和完成的工作量计数。冻结后，用一条可重复的命令输出指标，采样次数要足以消除噪声（取 N 次的中位数，而不是单次运行）。在做任何改动之前，记录基线指标以及回归门禁（必须持续通过的测试）的一次全绿运行。
3. 通过 **show-me-your-work** 技能开启决策日志。一个 `decision.tsv`，每次尝试一行：id、hypothesis、change、before、after、delta、tests、verdict（kept 或 reverted）、note。每次尝试前先阅读它。将其置于版本树之外（gitignored）。
4. 让每个假设都基于第 1 步的架构模型，使其指明一个具体机制（"把 X 从启动路径上推迟，因为它会阻塞首次绘制"），而不是"试着做点记忆化"。对于性能指标，按 Perf issue playbook（`playbooks/perf-issue.md`）第 2 步中的性能箴言来排列假设。只借用它们的顺序，不要借用那一步的停止规则。
5. 循环，每次迭代一个假设：
   - 使用你配置的 hillclimb 模型（默认 `claude-opus-5-5-xhigh-fast`）把改动交给一个范围严格受限的子代理。根据 Subagents 一节，为每个子代理选择适合该任务的推理级别。监督并审查 diff，而不是自己动手敲代码（**guard-the-context-window** 原则技能）。当有多个独立假设同时进行时，把它们分派给并行的子代理，每个子代理使用自己的工作树（worktree）（**separate-before-serializing-shared-state** 原则技能）。
   - 用冻结后的框架测量改动前后，并运行回归门禁。
   - 只有当指标变化超出噪声且门禁保持全绿时才接受。否则完整回退该改动。"可能有用"的调整不予保留。
   - 每个被接受的修复提交一次，只暂存你改动过的文件（`git add <files>`，绝不用 `-A`）。无论保留还是回退，都要记录该行。
   每次迭代都以一次检查结束，然后才开始下一次（**sequence-verifiable-units** 原则技能）。如果运行是无人值守的，只借用 Autonomous run playbook（`playbooks/autonomous-run.md`）中的唤醒机制，不要借用它的停止规则。
6. 越过第一个平台期。遇到停滞、连续几次被拒时，转换类别、组合那些差一点成功的方案、重读源码，或者尝试更激进的做法，然后再下结论说这座山已经爬到顶。正确性和简洁性优先于数字。如果一次"成功"破坏了行为，就回退它；如果一次简化保住了数字，就保留它（**laziness-protocol** 原则技能）。
7. 当停止谓词被满足时停止，或者当剩余的想法都收效甚微、不值得其成本时停止。不要为了满足谓词而放宽谓词，也不要在还有低成本的未尝试假设时就放弃。如果卡住了，就把它暴露出来，而不是空转。
8. 运行 **Opening a PR**，按被接受的提交落地的顺序堆叠它们。

**答复：** 指标与目标、从基线到最终结果及百分比变化、运行的迭代次数（保留 vs 回退）、每个被接受的修复各占一行、`decision.tsv` 的路径，以及如果继续推进你会尝试的最佳下一步想法。

### Autopilot-full

**你负责裁决，绝不负责 PR。每个 PR 由一名 owner 从构建到合并全程负责，在你的集群（它从未编写过代码）证明落地的代码之前，任何东西都不会合并。**

一个裁决覆盖一个补丁，而绿色的 CI 只覆盖一个 head。第 4 步运行一次完整集群，并且仅在重大改动时再运行一次。`playbooks/shipping.md` 中的 patch-id 规则可以沿用某个 lane 的结果，而每个新 head 都需要它自己的绿色 CI。

1. **操作者的闸门优先。** 授权只覆盖队列中的条目，因此操作者指明归他们的条目以及队列之外的 PR 停在 merge-ready。要求陈述计划并不代表放行。
2. **每个 PR 派生一名 owner，并把它的工作放在替代品能找到的地方。** 为整个项目解析一次 forge。GitHub CLI（`gh`）是默认。如果 `command -v origin` 成功且 Origin 能解析仓库，则对每个 PR 操作使用 `origin pr`。否则留在 `gh` 并记录回退。绝不要求 Graphite（`gt`）。每个 owner 都是一个 Cursor 云端代理，它进行构建、按 `playbooks/opening-a-pr.md` 打开其 PR、在真实产物上证明改动、按 `playbooks/babysit.md` 照看到绿色，并在第 4 步和第 5 步放行后合并。在该 playbook 要求报告 rebase 的地方，owner rebase 它自己的分支并用 `git push --force-with-lease` 发布它。

   尽早打开 PR，让 CI 和机器人与工作并行运行。代码只有在 slop-strip（`cursor-team-kit` 插件的 `deslop` skill（`/deslop`））和 `/no-comments` 处理之后才算就绪，因此完整集群在成品代码上运行。然后在自证之前 rebase 到当前主干并报告代码就绪的 head，以便验证运行在补丁将要落地的基础上。报告每个后续的 head，并在自证、CI 和 babysit 完成后达到 merge-ready。修复轮次停在该基础上，除非主干冲突、破坏 CI，或已知并发落地了对相同文件的改动，因为每次 rebase 都会重启 CI。在代码就绪推送之前，以及在需要验证器的后续推送之前，对提交 head 上受影响的路径运行仓库的检查。

   假设虚拟机会挂。启动后不久，按 **show-me-your-work** skill 在根代理的存储（系统提示中的路径）中推送并启动一条决策记录，然后在开始下一个之前推送每个完成的单元。任何派生子代理的人都在该存储中记录它的 id、状态和根据过去同类运行得出的 stuck-after 运行时长，以便父代理挂掉时根代理可以探测它。只对你自己的分支强制推送，并用 `--force-with-lease` 固定到你上次推送或接管的 SHA；对于任何不是你发起的推送，停下来向根代理报告。
3. **让 owner 并行运行于主干之外，绝不堆叠，** 以便每个 PR 独立落地。
4. **集群验证一次。** 完整集群在代码就绪的 head 运行一次。另一次完整集群仅在有新行为、重新设计或大型新 diff 时运行。一次 rebase、一次合并冲突解决或小修复在新 head 只需一个验证器，而仅措辞变更则不需要。按 **swarm** skill 在代码就绪的 SHA 并行展开独立验证器。它们重新运行闸门，通过其控制 skill（例如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或具名驱动器在真实界面上现场证明承重行为，并审查 diff。没有现场 lane 的裁决不算干净，在你审查 merge-ready 报告的凭据之前也不算干净，因为没有 lane 会信任它未检查的声明。

   只针对你能展示的问题阻塞 PR，即在 head 上的失败运行或被 PR 改错的一行文档。PR 的基础（无论是主干还是堆叠中它下面的 PR）已存在的问题不阻塞，除非 PR 复制了它或新近触及它。只有用户会遇到的 bug、失败的闸门或错误的已发布文档才阻塞，其他一切放进后续事项。
5. **owner 只合并你验证过的、在它将落地的主干上测试过的内容。** 单凭绿色 CI 永远不授权合并。一旦集群的 lane 启动，合并准备就 rebase 到当前主干、报告新 head 并等待绿色 CI。

   就在合并之前，获取主干并询问它的改动是否可能影响补丁，因为为每个主干变动都 rebase 永无止境。当将要落地的代码从未被测试过时，例如冲突、双方都改过的文件、或 PR 运行哪些检查发生了变化，则 rebase 并等待 CI。双方都改过的 lockfile，如果在合并结果上冻结安装通过，且 PR 改动的包在那里解析得与在 head 上一样，则无需 rebase，因为该安装测试的是将要落地的 lockfile，而安装失败意味着 rebase 必须修复它。当主干改了补丁的调用方或补丁依赖的东西，例如它调用的代码或依赖版本，在合并结果上运行补丁的检查，通过则合并。否则直接合并。如果主干会迫使在合并准备之后再 rebase 第三次，则暂停并向根代理报告，由根代理排序冲突的工作。
6. **运行根层。** 任何放宽闸门的动作，例如提高预算或添加 allowlist 条目，都需要验证器的证明，然后由你重新副署，因为 owner 正是想要绿色的一方。在覆盖审批的授权下，该副署就是审批，owner 对它的记录指向你的副署供 lane 检查。被禁用或软失败的检查总是要移除，因为它不再守护每一种情况。永远不要给出或绕过 forge 强制执行的审批，因为没有副署能覆盖它。

   在操作者放行后，启动 `/loop 1h` 进行审计直到没有委托的工作剩余，因为长时间运行会漂移且代理会静默停滞。每次 tick 从主干重新读取本 playbook 并修复漂移，例如未报告的 head 或未记录的代理，让它的 owner 记录下来，因为漂移是记录中的缺口，而非停滞。它探测每个代理，一直到叶子 lane，并根据其副作用判断每个代理，因为状态文本和摘要可能掩盖卡住的子代理。当代理出错、无法启动回合，或超过其 stuck-after 运行时长没有新动静时，它就卡住了，首次 tick 时既没推送也没写记录行的 owner 同样如此。等待你或操作者的不算卡住，所以回应它。立即替换卡住的代理，不等它的停止落地。为操作者改变了一些东西的 tick 以按 **ketchup** skill 向其同步收尾，什么都没改的 tick 保持安静。
7. **操作者喊停时立即停手。** 一条 hold 以零写入命令传达到每个 owner。每个 owner 报告它所处的位置并保留其简报，直到操作者解除。

**回复：** 按 **ketchup** skill 向操作者同步，涵盖每个 PR 的状态和裁决、合并了什么、副署及原因、未决的操作者闸门，以及搁置的后续事项，并附上每个 PR 和记录的链接。

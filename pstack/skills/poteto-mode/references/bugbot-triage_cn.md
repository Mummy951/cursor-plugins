# Bugbot 分流

当 Babysit playbook（`../playbooks/babysit.md`）处理 Bugbot 或 review 自动化评论时，使用本参考。目标不是默认忽略 Bugbot。目标是停止把每条评论都当作必须的代码改动。

## 决策标准

在采取行动前对每条 Bugbot 讨论串（thread）分类：

- `fix`：评论指出了一个可能正确的正确性、安全、隐私、数据丢失、认证、计费、迁移、幂等性、竞态或已发布行为问题。在最低层的所属 PR 中修复它，然后用 commit SHA 回复并解决该讨论串。
- `dismiss`：评论符合有记录的低风险噪声模式，且当前代码/上下文证明该担忧不需要代码改动。用简短理由回复并解决该讨论串。
- `ask`：评论是新颖的、高严重性的、与安全/隐私/数据相关的，或含糊不清的。询问用户，而不是猜测。

有疑问就询问。跳过一条噪声式的代码质量评论代价很小；跳过一个真实的数据或安全 bug 则不然。

## 已学习模式格式

按以下格式添加未来的模式：

```markdown
### <简短模式名称>

- 置信度：candidate | recurring | strong
- 跳过条件：<必须为真的条件>
- 不跳过条件：<风险边界>
- 示例信号：<识别该模式的短语或代码上下文>
- 来源：<PR/评论 URL 或简短的历史说明>
```

对一两个示例使用 `candidate`。在多次真实驳回后使用 `recurring`。只有当模式范围狭窄、经过反复验证且低风险时才使用 `strong`。

## 反复出现的跳过候选

### 有意为之的 UI 或设计系统视觉变更

- 置信度：candidate
- 跳过条件：PR 描述、截图、设计 review 或附近代码明确说明了该视觉变更，且 Bugbot 的评论只是重述某个共享视觉默认值发生了变化。
- 不跳过条件：评论指向无障碍访问、焦点可见性、键盘导航、颜色对比度，或 PR 并未有意更改的组件 API 契约。
- 示例信号：关于焦点轮廓、按钮大小、间距或共享组件视觉默认值的评论，而负责人回复"intentional"或"intended"。

### Bugbot 看不到的上游栈或栈内局部用法

- 置信度：candidate
- 跳过条件：Bugbot 将某个 export、组件、helper 或文件标记为未使用，而当前 forge 的 PR 列表和 diff、上游栈的 diff 或 PR 上下文显示它被该 stack 中较后的某个 PR 使用。
- 不跳过条件：当前 PR 不属于某个 stack、该符号是公共 API，或所谓的上游用法无法验证。
- 示例信号："Exported component is never used"，并有人回复类似"used upstack"。

### 并行实现期间的临时重复

- 置信度：candidate
- 跳过条件：PR 有意重复少量代码，使新路径与被删除、被替换或正在验证的旧路径并行存在。
- 不跳过条件：重复的代码改变了安全、计费、数据访问、API 行为，或者引入一个长期存在的共享抽象显然会降低风险。
- 示例信号："Significant duplication"或"duplicated validation logic"，而负责人解释旧路径将被删除，或重复逻辑是有意保持局部的。

### 现有框架或组件的不变式已覆盖该警告

- 置信度：candidate
- 跳过条件：该担忧已被当前 diff 或附近代码中可见的共享组件、框架契约、类型不变式或单一事实来源所保证。
- 不跳过条件：该不变式只是被假设而未强制执行、依赖时序，或跨越了值可能分叉的异步/状态边界。
- 示例信号：关于内部 popover 缺少 max-height 的评论，而共享 popover 已经强制了视口边界；或者关于可空值的评论，而本地检查的值和传入的值来自同一来源。

### 负责人声明的后续跟进或延迟清理

- 置信度：candidate
- 跳过条件：PR 负责人明确表示这是一个已知的后续跟进项，当前 PR 没有使该行为变差，且评论不涉及高风险领域。
- 不跳过条件：agent 在没有负责人输入的情况下行动、问题是中/高严重性的产品行为，或延迟会合并进一个新的回归。
- 示例信号："I'll worry about that later"或"we'll delete this eventually"。

### 自行撤回或明确为误报的规则评论

- 置信度：recurring
- 跳过条件：评论正文或之后的 Bugbot 回复明确表示该发现已撤回、已合规或是误报，且 agent 能在本地验证相关规则。
- 不跳过条件：唯一的证据是某人在未作解释的情况下称一个高风险问题为"false positive"。
- 示例信号：一条文件命名规则的评论，其正文说明该文件已经合规。

## 默认询问

不要自动跳过这些类别，即使之前的 PR 驳回过类似内容：

- 安全、隐私、认证、计费、数据保留、训练数据和权限边界方面的发现。
- 高严重性的发现。
- 迁移、schema、幂等性、并发和跨系统行为方面的发现。
- 那些建议的修复很小、且在不改变产品意图的情况下明显降低风险的评论。

历史数据显示，人类有时会驳回安全/数据流相关的评论。把这些当作负责人的判断决定，而不是团队级的跳过规则。

## 来自近期 babysit 的候选经验

在 babysit 期间或之后，当新的候选经验看起来对团队有用但尚未成熟时，把它们追加到这里。一旦有多个 PR 证实某个模式，优先把反复出现的候选提升到上面的章节。

### 手动重新实现浏览器原生行为

- 置信度：candidate
- 跳过条件：实际上从不跳过。当 diff 用手动等效实现替换浏览器原生行为时（原生 sticky → JS 定位的克隆、原生滚动定位 → 转发的 wheel/touch 事件、绘制顺序遮挡 → masks/clip-path），Bugbot 针对该代码的逻辑 bug 发现一直都是合理的。
- 不跳过条件：发现涉及事件转发的缺口（wheel deltaMode、touch 平移、边缘处的滚动链式传递、tap slop）、mask/clip 的命中测试差异，或此类代码中 observer 与 React 状态之间的时序竞态。默认修复。
- 示例信号："masks do not affect hit-testing"、"overlay blocks wheel scroll"、"ignores deltaMode"、"runs in the IntersectionObserver callback before React applies state"。
- 来源：一个 sticky 遮挡相关的 PR：六轮 Bugbot，约十八条发现，每一条都是修复而非驳回。

### 契约测试漂移的断言很容易验证——先运行测试

- 置信度：candidate
- 跳过条件：永远不要跳过验证本身；它只花一条命令。当一个 PR
  附带一个固定协议或文档措辞的契约测试（对 SKILL.md 的正则、
  文档措辞的快照），而 Bugbot 声称"测试不再与文档匹配"
  （或反之）时，在分类之前先在 PR tip 上运行该测试。
  一次变红（失败）的运行从经验上证实了该断言；一次变绿的运行则是
  用于驳回回复的具体反证。
- 不跳过条件：不适用——这是一个验证捷径，而不是驳回模式。注意，重复的
  倾向于驳回的启发式方法在这里会失效：固定措辞的测试发生漂移，
  恰恰是因为之前的修复轮次编辑了措辞。
- 示例信号：某个 PR 上出现"契约测试遗漏了修复前的等待"，而该 PR
  较早的修复提交重写了被固定的段落；在 tip 上运行的测试恰好在
  被引用的断言处失败。
- 来源：一个固定措辞的 PR，经历了八轮 Bugbot；尽管之前每一轮
  都被修复并解决，该断言在第 7 轮仍是真实的。

### 过时且已在同一 PR 稍后修复的安全 review 发现

- 置信度：candidate
- 跳过条件：一次 agentic 安全 review（或类似的）声称缺少某个 authz/验证调用，而当前 PR tip 明确包含那个确切的关卡（带测试），通常是在 review 运行之后的一个加固提交中添加的。
- 不跳过条件：所引用的 helper 对讨论中的主体（principal）是空操作、检查在其所守护的副作用之后运行，或缺少对所声称主体的覆盖。
- 示例信号：一条 HIGH 级别的"missing authorization check"发现，而在 tip 上确切的守卫已经在副作用之前被调用。
- 来源：一个 webhook 端点的 PR，其加固提交的时间晚于 review 运行。

### 扩大刻意收窄的错误条件会掩盖真正的错误

- 置信度：candidate
- 跳过条件：该发现要求把一个狭窄的错误条件（某个特定的 `errno`、
  错误码或状态类别）扩大为包罗万象的兜底，而这种狭窄性
  编码了一个真实的区分。典型形态是一个以 `ENOENT` 为门槛
  的依赖项回退："二进制未安装"与"命令运行了但失败"是两种
  不同的情况。对任何非零退出都重试，会把一个合法的失败
  （未找到、认证过期、网络）拿去走回退，然后报告回退的错误，
  从而掩盖真正的错误。
- 不跳过条件：该狭窄条件遗漏了同一类别中的某个情况（另一个"二进制
  不可用"的 errno，如 `EACCES`，或另一种传输层失败）、未处理的
  路径会丢失数据或留下部分状态，或者重试是幂等的且原始错误仍会
  被暴露。
- 示例信号："only retries when X fails with ENOENT … never tries the
  fallback even when a working Y exists"，指向这样的代码：其回退是
  为缺失的依赖项而设，而不是为失败的操作而设。
- 来源：一个 CLI 重命名的 PR，其回退是为缺失的二进制而设，
  而不是为失败的命令而设。

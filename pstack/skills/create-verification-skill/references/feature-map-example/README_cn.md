# Notes 验证映射

本目录是用于验证 Notes 面向用户行为的维护源。在驱动应用之前先阅读索引，然后使用对应的功能文件作为操作指引。

## 基线前置条件

- 使用一次性数据目录在 `http://127.0.0.1:4173` 启动 Notes。
- 设置 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，使并发运行不共享状态。
- 预置标题为 `Quarterly plan` 和 `Grocery list` 的笔记。
- 将 `control-notes` 和 `notes` CLI 加入 `PATH`。
- 运行 `control-notes doctor`，并要求 URL、数据目录和构建版本符合预期。
- 绝不要驱动并非由此验证运行启动的实例。

## 驱动约定

- 除非前置条件另有说明，否则每个操作指引都从基线状态开始。
- 优先使用 ARIA 角色和无障碍名称，而非 CSS 选择器或 DOM 位置。
- 将每条命令都按字面处理。保持带引号的名称和标志不变。
- 通过 `control-notes browser` 执行浏览器操作。
- 通过 `control-notes cli -- <command>` 执行终端操作。
- 变更之后恢复预置数据。清理时不要删除证据产物。

## 证据与跳过报告

- 记录用户操作及由此产生的状态，而不只是最终画面。
- UI 证据包括 ARIA 快照和一张显示应用标识的截图。
- CLI 证据包括命令、stdout、stderr 和退出码。
- 变更证据包括对所存储值的只读二次查看。
- 为每项产物记录所使用的功能 ID 和入口点。
- 报告无法到达的路径时，附上尝试的命令和未满足的前置条件。
- 不要将已跳过的入口点报告为通过其他路径已验证。

## 功能条目约定

每个功能文件以 H1 标题和一段描述用户可见行为的段落开头。然后恰好使用按此顺序排列的四个 H2 章节。

1. `Sub-features` 列出简短 ID，每种行为占一行。
2. `How to get to it (user POV)` 列出每个用户入口点。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，使用带标签的列表项，将每个用户操作与精确的命令和可观察的结果配对。
4. `Gotchas` 列出可能浪费或使验证运行失效的陷阱。

不要在映射中包含实现细节。只命名用户路径、稳定句柄、所需状态、命令和可观察的证据。

## 功能

- [Create a note](./create-note.md) 涵盖浏览器和 CLI 创建、取消、持久化和清理。
- [Search notes](./search.md) 涵盖工具栏、键盘和 CLI 搜索，以及匹配、空和清除状态。

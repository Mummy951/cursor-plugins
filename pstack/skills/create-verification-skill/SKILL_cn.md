# 创建验证技能

每个严肃的项目都需要一种脚本化方式来驱动真实应用并证明其行为：启动它，像用户一样练习某个功能，并捕获证据。本技能会将其生成为针对该仓库定制的项目本地技能（`.cursor/skills/verify-<app>/`）。你编写的是生成器的输出，给下一个智能体使用，而不是给人类：它会被一个从未见过该应用的智能体在任务中途冷启动阅读。

## 1. 访谈仓库，而非用户

从代码库中回答这些问题，只询问你无法观察到的内容：

- **Surface（界面）：** 用户实际接触的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用，还是库？一个仓库可能有多个；挑出主要的那个，并记录其余的。
- **Run（运行）：** 应用如何在本地启动？优先使用仓库自身文档化的开发命令（package scripts、Makefile、README 快速入门）。记录端口、环境变量、种子数据、认证。
- **Drive（驱动）：** 智能体如何以编程方式与之交互？优先使用已有的测试框架——Playwright/Cypress 规格、expect 脚本、PTY 辅助程序、可 curl 的端点、调试端口。然后才选择通用方案：Web 和 Electron 用 browser/CDP，CLI/TUI 用 tmux/PTY 框架，服务用纯 HTTP。
- **Observe（观察）：** 可以捕获哪些证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **Isolate（隔离）：** 两个实例能否并行运行（端口、数据目录、配置文件）？如果不能，在生成的技能中说明：拒绝双重驱动一个共享实例，胜过破坏用户的会话。

如果检出的代码无法按原样构建或启动，先修复它（或精确报告问题），然后再生成；针对损坏的基础编写的技能会教出错误的步骤。当无关的缺失资源阻塞启动时（API 从不提供服务的静态目录、示例配置），生成的技能可以创建它，明确标记为验证脚手架，并在清理时移除。

## 2. 生成技能

写入 `.cursor/skills/verify-<app>/SKILL.md`，包含 YAML frontmatter（`name: verify-<app>` 以及一个 `description`，它要命名应用、界面以及何时使用它——没有 frontmatter，技能永远不会注册）和以下各节，每一节都基于访谈实际发现的内容（不留占位符）：

- **Launch（启动）：** 启动应用进行验证的精确命令，以及如何判断它已就绪（日志行、提示符）。启动必须能从空数据目录达到可用状态，包括任何迁移和种子数据。就绪意味着可用，而不只是某个进程有响应。数据库健康检查可能通过，而其初始化脚本仍在运行。包含拆除（teardown）。对于短生命周期的 CLI 或 TUI，没有需要保持活动的服务器：启动意味着构建一次二进制文件（或安装依赖），然后在各自隔离的 PTY 或 tmux 会话中启动每次驱动。
- **Doctor（诊断）：** 一个只读检查，回答"这个实例值得驱动吗？"——进程已启动、版本/构建正确、端口由我们占用、认证有效。当任何事情看起来不对时，智能体首先运行它。
- **Drive（驱动）：** 带有本仓库真实选择器/命令的框架方案，而不是示例。优先使用稳定的句柄（ARIA 标签、data 属性、提示字符串、路由路径），而非坐标和 Tab 顺序。
- **Evidence（证据）：** 为证明要捕获什么以及存放位置。声明证明标准：练习真实用户路径，而非内部 setter 或仅用于测试的接口；捕获动作及由此产生的状态，而不只是最终画面；验证副作用（写入的文件、插入的行、发送的消息）与可见内容一致；仅在已有生产边界隔离外部系统的地方使用 mock。当安全路径是 dry-run 或测试模式时，通过观察（文件、网络、git refs）验证它实际跳过了什么，而不是相信它的名字：某些 dry-run 仍会访问网络或打开浏览器。
- **Cleanup（清理）：** 如何拆除运行创建的实例。永远不要按进程名杀进程；只杀掉你自己启动的。清理移除实例和临时状态，绝不移除证据：证明工件在拆除后仍然存在，位于技能指定的位置。
- **Helpers（辅助脚本）：** 技能附带的任何脚本都是可执行的，且其调用方式在技能正文中展示。读者需要逆向工程才能理解的辅助脚本不算辅助脚本。

## 3. 播种功能地图

创建 `.cursor/skills/verify-<app>/features/README.md`，以及每个你能识别的用户可见功能各一个文件（一开始以最重要的 3-5 个为目标，来自路由、命令、菜单或文档）。遵循 [`references/feature-map-example/`](references/feature-map-example/) 中的形状，带一个 README 索引和每个功能一个文件。每个文件从用户视角回答：该功能是什么、如何到达它、如何用框架驱动它，以及什么可观察的最终状态证明它有效。四个 H2 标题是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果种子数据缺少某个旅程需要的前置条件，该旅程会报告失败，原因写入该功能的 `Gotchas`。绝不为让旅程通过而弱化旅程。地图是仓库维护的验证源；当地图列出其他入口时，只驱动一个方便入口的证明是不完整的。

## 4. 在交付前验证生成的技能

端到端运行一次它自身的指令：启动、诊断、驱动一个已映射的功能（一个就够；地图的存在是为了让后续运行覆盖其余部分）、捕获证据、清理。清理后，确认证据仍存在于指定位置——吃掉证明的清理会通不过这一步。修复失败之处，并且在每次失败的迭代后也运行生成的清理，以免失败的尝试遗留进程和端口。一个从未被执行过的生成技能只是草稿，不是交付物。如果你在真实目标的替代物中验证了它（用容器代替全新 VM，用本地栈代替远程栈），列出替代物做了而目标不会做的每一个设置步骤。这些步骤在真实目标上运行覆盖之前保持未验证状态。

## 5. 提供维护循环

将用户指向 `/maintain-verification-skill`，以便在应用变化时保持地图的准确。仅在他们询问时才建议节奏。

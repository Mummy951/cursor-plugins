# 状态图（Statechart）

图用阅读它的人的语言展示一个系统如何在状态之间迁移。那个人，也就是读者，决定这样的行为是否正确。

## 运行

在仓库外的一个临时文件夹里工作。写一份 TLA+ spec 及其 config。然后运行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，所以要用能执行 TypeScript 的运行时来运行它。`scripts/statechart` 是一个 POSIX shell 脚本，它会挑选一个运行时。在原生 Windows 上，用 Node 22.18 到 22.x，或 Node 23.6 及以上版本运行 `node --disable-warning=ExperimentalWarning <skill dir>/scripts/statechart.ts`。

首次运行会用 mise 安装 TLC 和 Java，需要联网。

## 编写 spec

- 把读者认同的每一条规则写成一个 INVARIANT。一条规则可以是关于某个画面、某个结果、某个存储值或某条消息。如果模型里没有对应某条规则的变量，就加上这个变量。绝不要为了让它成立而削弱规则。
- 把 `Next` 写成各动作的析取，例如 `YouPressPlay \/ YouPressStop`。如果不这么做，TLC 会把每一步都命名为 `Next`。
- 一个没有出步的状态会破坏 `NoDeadlock`，即使它是一个正确的结束状态。当某个 INVARIANT 或 PROPERTY 已经用了这个名字时，规则就是 `CHECK_DEADLOCK`。给 `Next` 加上一个仅在结束状态为真且什么都不改变的动作，例如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 中给它一个标签。

## 选择图

做那些需要判断的工作：每个状态和箭头上的文字、阶段及其颜色、标题，以及给读者的报告。把你的工作放进一个 view 模块，并用 `--view` 提供它。

要展示读者的语言，view 导出 `state(vars)`。`state()` 返回的值决定形式：

- 字符串给出一张扁平的图：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 数组给出父状态：`export const state = (v) => v.main.split(".");`
- 对象为每个键给出一个并行区域：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

用读者能看到或关心的东西给每个状态加标签，例如 "Paying" 或 "Lease held, write pending"。不要让变量名出现在标签里。在 `vars` 中，TLA+ 序列是一个键从 1 开始的对象，所以 `v.pc[1]` 就是 `pc[1]`。集合是一个数组。

view 还可以导出 `step(action, from, to)`。它得到 TLC 的动作名称以及该步之前和之后的值，并返回箭头的标签。把每一步的标签写成用户看到它发生时的样子，例如 "you press play" 或 "the connect fails"。不要命名代码或 TLA+ 动作。在图中结果相同的两个动作得到相同的标签，这样它们就共用一支箭头。

当某一步只在某些条件下才会发生时，用读者的语言把条件写在标签末尾的方括号里，例如 `you press play [while the file loads]`。在区域图中，命令会把针对其他区域的条件写在箭头上，用它们标签的语言，例如 `[when Offline]`。你的方括号会取代它，于是一状态发出的两支箭头可能看起来一样。所以在区域图中，不要为针对另一个区域的条件写方括号。当一个没有标签展示的值决定了某一步走向何处时，在标签中点出结果，例如 "the roster read fails"。

view 还可以导出这些内容：

- `group(vars)` 返回一个阶段的名字。每个图状态获得其所在分组的颜色。当一个图状态背后的模型状态处于不同分组时，该状态不着色。
- `colors` 为每个分组名指定一个颜色类。
- `title` 是一个字符串，图会在顶部显示它。

命令对每个模型状态最多调用一次 `state()` 和 `group()`，对每一步最多调用一次 `step()`。图和报告都使用这些答案。所以要让每个函数只依赖于它的参数。

图不会画出停留在一个标签内的步。当读者必须看到这样一步时，拆分该标签。

目标控制在大约 20 支箭头或更少，因为更繁忙的图难以阅读。先从 `state()` 返回更粗的标签。给行为相同的值一个标签，并省略读者不需要的细节，例如一个返回不改变任何东西的飞行中调用。保留 bug 路径的每一个状态，保留每一个标记。当一次合并把一个 `breaks` 状态变成 `mayBreak` 时，它会掩盖规则在哪里被破坏。不要合并两个破坏不同规则的状态，因为那样读者就看不到哪条规则在哪里被破坏。如果图仍然太繁忙，对读者不需要的步从 `step()` 返回 `null`，例如每个状态都有的重置，或箭头重复了其他箭头所示内容的步。隐藏步时要遵守这些规则：

- 保持每个图状态都能通过从某个起始状态出发的箭头到达。
- 对模型中存在出步的每个图状态，至少保留一支出箭头。
- 要么隐藏一支箭头的全部步，要么一个都不隐藏。只隐藏一部分会使其条件变窄。
- 在交接中说明图隐藏了哪些步。

## 阅读报告

- 在图中，破坏规则的状态带有 `breaks` 类。当只有它背后的部分模型状态破坏规则时，它带有 `mayBreak` 类。图例（Legend）给出每个标记对应的规则。当两条规则都被破坏时，它会在一个标记上同时给出两者，所以要在交接中说明哪个状态破坏哪条规则。在区域图中，当一个状态被每个包含它且可能破坏规则的区域状态组合所标记。当一个组合可能破坏规则而它的所有状态都没有标记时，该组合中的每个状态都会得到一个标记。
- TLC 会越过破坏规则的状态，所以图会展示 bug 之后的状态。
- 因为 TLC 会越过 bug，一个对状态数没有限制的模型可能无休止地运行。保持常量较小，或添加 CONSTRAINT。
- 有了 VIEW 或 SYMMETRY，TLC 会把它视为相同的那些状态计为一个状态，图也只画那一个状态。一支箭头可能指向它而不是该步实际到达的状态，报告会说明这一点。
- TLC 会检查越过 CONSTRAINT 或 ACTION_CONSTRAINT 的每个状态中的规则，但不会探索该状态，也不会检查它是否死锁。当 TLC 对某条规则的最短路径结束于这样一个状态时，图会画出该状态，报告给出该路径。图不会画出越过边界的其他状态。这样一个状态中的死锁不会显示出来。TLC 也会检查被 ACTION_CONSTRAINT 排除的每一步之后的规则，即使它以另一种方式到达了下一个状态。当 TLC 对某条规则的最短路径以这样一步结束时，图会画出那一步。
- 命令会按写好的 config 用单 worker 通过 TLC 检查规则。当某条规则被破坏时，命令会移除那条规则并再次运行 TLC，直到没有规则被破坏。第一次破坏之后，每次运行都会在 10 万个不同状态处停止，这样大模型就不会无休止地运行。当一次运行到达该上限或因错误而停止时，报告会在 "Rules not checked" 下列出它未检查的规则，图也不会标记它们。一条未被检查的规则可能成立也可能被破坏。要检查它，请从 config 中移除被破坏的规则，或缩小模型。该上限会添加一个改变 TLC 变量顺序的模块，所以对于一个 property，TLC 可能找到与不带上限的运行不同的反例。
- `tlc.out` 是按写好的 config 运行 TLC 时打印的内容。当图没有显示某条被破坏规则的 bug 路径时，`tlc-RULE.out` 是找到它的那次运行中 TLC 打印的内容。当 TLC 重复它的第一条警告时，原生 TLC 会打印两次，但 `tlc.out` 只显示一次，因为 TLC 把第二份排除在本命令读取的输出之外。这只在 Java 使用 `-XX:+UseParallelGC` 运行时发生，否则 TLC 的第一条警告是建议传入该标志，且只打印一次。

## 展示图

把 `chart.mmd` 作为 `mermaid` 代码块展示给用户。图的预算是 500 个状态，由 TLC 按写好的 config 统计。超过这个数时，图只画通向被破坏规则的路径，而当没有规则被破坏时，命令不写出 `chart.mmd`。它仍然检查每条规则，报告给出状态数和每条 bug 路径。要看完整的图，请缩小模型。

用 Pele 渲染图。当用户要求图片，或某个图太大而无法作为文本阅读时，遵循 `references/render.md`。除非用户要求，不要使用其他渲染器。

## 交接

把每张图及其 Mermaid 文本交给必须做决定的人。为每条 bug 加一行：规则、读者对那条规则的句子，以及报告编号给出的路径。说明模型省略了什么。给出重新生成这些文件的命令，使用一个全新的 `--out` 文件夹。

当模型描述的是代码时，把每条 bug 路径对照真实代码重放，作为测试或现场复现，每个动作对应一步。如果某个 bug 没有发生，就认为模型是错的，直到你证明它不是。

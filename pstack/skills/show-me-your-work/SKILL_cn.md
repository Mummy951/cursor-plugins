# 给我看你的工作（Show me your work）

维护一份唯一的规范日志。

## 格式

一个 TSV 文件，每条决策一行。单元格保持单行。证据是一个指针，而不是一段散文。

复制 `references/decision-log-template.tsv`（表头行）来开启一份干净的日志。列包括：

- **ts.** ISO8601 时间戳。
- **phase.** 阶段或工作流。
- **decision.** 选择或做了什么，一行。
- **why.** 用大白话说明原因。如果某条原则驱动了它，就直白地说出来，而不是当作一个行话标签。
- **evidence.** 一个能证明它的链接或路径：提交 SHA、PR 编号、`file:line`，或者一个产物、追踪记录或截图的路径。绝不要是一段话。
- **result.** 结果或谓词状态：`tests green`、`reverted`、`pixel-diff 0`、`INCONCLUSIVE`、`open`。

下面是一个例子，用大白话写成，让审阅者一眼就能读懂。

```
ts	phase	decision	why	evidence	result
2026-05-24T09:02:00Z	frame	先统计工作量，大约 100 个组件、约 75 小时	想在开始一次长时间运行前知道规模	commit 3a9f1c2	发现开工前有 5 件事要理清
2026-05-24T09:40:00Z	harness	在改动任何东西之前先给旧版本截图	这样我们可以新旧对比，捕捉任何视觉变化	scripts/snapshot.sh, baseline/	保存了 120 张参考截图
2026-05-24T11:15:00Z	widget	把 widget 样式迁移过来，不改变其外观	保持改动小、结果一致	commit 7c21e0a, pixel-diff 0	看起来完全一致，测试通过
2026-05-24T12:30:00Z	widget	丢弃了一个助手的工作，因为它的截图是空白的	检查真实文件，而不是相信它的总结	worktree reset	已回滚，并收紧了下次的指令
```

## 记录一行

像你会向队友说明你做了什么那样写每一条。用大白话、具体的动作，不要 AI 腔或抽象行话（**unslop** skill 同样适用于日志文本）。

使用辅助脚本 `scripts/log.sh <logfile> <phase> <decision> <why> <evidence> <result>`。它会打上 `ts`，首次使用时写入表头，去掉多余的制表符/换行符，并给任何以 `=`、`+`、`-` 或 `@` 开头的单元格加上单引号前缀。用裸 `printf` 追加一行也可以，但如果单元格来自生成或用户提供的文本，要注意同样的字节问题。

记录决策点和检查点，而不是每一个动作：选择了一个分叉、完成一个单元及其验证结果、一次转向或回滚及其触发因素、浮现的阻塞、修复的关卡。对于循环运行，每次迭代记一行。跳过琐碎和显而易见的事。

一次运行是一个 agent 会话，包括它后续的轮次及任何对它的总结。一次接续、一个替换 agent 或一次新聊天都会开启一次新运行。当一次运行向已有行的日志追加内容时，它的第一行 phase 为 `start`，在另一次运行的 `start` 行之后的第一行也是如此。因此在后续轮次回到某份日志的运行，会先读取日志的最后几行，看看自那以后是否有另一次运行写入过。一行 `start` 会写明在它之前、本次运行未写入的那些行的 `ts` 范围，其 evidence 指明本次运行，例如它的 agent id。`start` 这个 phase 不用于其他任何用途。

## 存放位置

默认情况下，日志是工作产物，不提交。把它放在工作目录的 `decisions.tsv`，当多个工作同时进行时放在 `.audit/<task-slug>.tsv`，并让它不进入 git。

只有当工作足够宏大、审阅者需要这条轨迹才能信任结果时才提交它。

## 规则

- 只追加。一个错误的决定会得到一个新行来取代它。绝不要编辑或删除历史。
- 优先使用由已提交脚本产生的证据，而不是手工临时拼凑的证据（**encode-lessons-in-structure** 原则 skill）。

## 对照会话记录审计日志

在运行结束时、交回之前，检查日志是否如实反映。读取当前工作区 `agent-transcripts/` 目录下本次运行的会话记录（系统提示会给出路径）。不要跨 `~/.cursor/projects/*/` 做 glob，那会读取无关的私人聊天。把本次运行的每一行与实际发生的情况逐一核对。每一段都始于本次运行的某个 `start` 行，或如果本次运行创建了日志则始于第一行，并止于另一次运行的下一个 `start` 行：

- 检查每一行都对应一个真实的决定或动作。
- 检查每一行的 evidence 都能解析，并显示该行所声称的内容。
- 一个塑造了工作但没有被记录的分叉、转向或被放弃的方案，就是一处缺口。把它补上。

修正日志，而不是修正故事。审计绝不编辑或删除某一行，即使是编造的行。当某一行既没有记录真实的决定也没有记录真实的动作，或者它的声称或证据有误时，添加一行用实际情况和一个能解析的指针来取代它。本审计不检查本次运行各段之外的行。如果本次运行自己的工作显示其中某一行有误，就象对待其他错误决定一样取代它。

## 对轨迹的跨模型审阅

在交回之前，生成一个使用与完成工作所用模型不同厂商模型的子代理。自我审阅不能替代它。该子代理读取审计轨迹和本次运行的会话记录，然后标出用户应当注意的内容。这不是重做工作，而是扫描其中不够理想或有风险的地方。根据 **poteto-mode** skill 的 Subagents 章节，为每个子代理按任务选择合适的推理级别。

- 证据薄弱或缺失的决策记录。
- 在会话记录中被跳过或声称已验证却无证据的验证步骤。
- 事后看来有风险的选择（过早、范围蔓延、掩盖症状）。
- 用户随意浏览时会错过的缺口。

每个产生了轨迹的运行的回复，都以一个 "Attention"（注意）章节结尾。用单独一行以审阅者的模型开头（`reviewed by <model>`），然后列出每一条标记，指向具体的行或时刻。"No flags"（无标记）是一个有效值。模型名称则不是。

## 审阅轨迹

从上到下阅读，跟随证据指针，抽查。GitHub 会把已提交的 TSV 渲染成表格。`column -s$'\t' -t decisions.tsv` 会在终端里渲染它。

## 组合本 skill

其他 skill 把它们的审计轨迹路由到这里，而不是另造一套。按名称引用它，并让它拥有该格式。不要复述这些列。

# TDD Bug 修复

当修复一个具有清晰、低成本测试路径的 bug 时，在改动生产代码之前先让出错的行为可执行。目标是一个聚焦于回归的测试：修复前失败，修复后通过。

如果测试不切实际，不要强行加测试。如果可用的测试需要大范围的脚手架搭建、脆弱的 mock、缓慢的端到端基础设施、仅存在于生产环境的状态、模糊的复现步骤，或大量无关的 fixture 改动，那就跳过新增测试，改用最接近的有效验证手段。

## 工作流

1. **理解 bug。** 找出预期行为、当前行为、受影响的路径，以及最小可观察的复现。
2. **选择最窄的可执行检查。** 优先使用已经用于该代码路径的最近的单测、组件测试、集成测试或回归测试。如果没有明显可行的测试路径，不要只是为了走流程而从零造一个。
3. **先写失败测试。** 加上能捕获该 bug 的最小聚焦测试。测试应当编码预期行为，而不是照抄当前实现。
4. **修复前先运行新测试。** 确认它因预期原因失败。如果它通过了，或因无关原因失败，在改实现之前先修正测试或复现。
5. **修复 bug。** 做最小的生产代码改动，使其满足预期行为，同时保留邻近的约定。
6. **重跑回归测试。** 确认测试现在通过。

## 当失败测试不切实际时

改用最接近的可执行回归检查：一个针对性的脚本、手动复现命令、浏览器自动化、快照对比、日志断言，或聚焦的集成检查。

宁可不加新测试，也不要加坏测试。坏测试是指这样一类：主要测的是 mock、编码的是当前实现细节、依赖时序或无关的全局状态、为一个小修复需要昂贵基础设施，或者在证明修复后立刻会被删除。

## 护栏

- 不要仅仅为了让测试匹配错误的实现而改测试。
- 不要削弱已有断言，除非预期行为确实变了且理由清楚。
- 让回归测试聚焦于该 bug。避免大范围 fixture 改动或无关的覆盖扩张。
- 如果 bug 是偶发的，尽可能让测试确定化，并记录被锁定的是哪个信号。
- 如果 bug 暴露出一类更广泛的失败，先落地聚焦的回归路径，再考虑增加相邻的覆盖。

## 最终回复

报告证据，而不只是结果：

- 说出修复前失败的测试或可执行检查，以及它产生的失败。
- 说出修复后通过的测试运行，以及所做的任何邻近验证。
- 如果无法给出修复前的失败证据，说明原因，并描述改用最接近的回归检查。

# 维护一个验证 skill

功能地图在应用变更的那一刻就开始腐坏。本 skill 是由 `/create-verification-skill` 生成的 skill（或任何带功能地图的项目本地验证 skill）的维护闭环。严谨度的单位是功能，而不是每一句话：要从源码覆盖每个功能文件，并实时演练每个功能，而不必把每一条要点都走到极致。

## 结果

选定其一，并说明是哪一个：

- **clean** — 每个功能都获得了源码覆盖和实时覆盖；没有值得提交的东西。不开分支，不开 PR。
- **changed** — 用一个 PR 提交经过证实的文档、harness 或地图修正。
- **blocked** — 覆盖无法完成，或经过证实的修正无法安全提交。准确说明是什么造成了阻塞。

## 编辑范围

只编辑验证 skill 自身的目录（其 SKILL.md、features/ 以及它拥有的任何 harness 脚本）。运行期间绝不编辑产品代码：地图描述了但应用已不再具有的行为，要么是文档漂移（修正地图），要么是产品回归（报告它，而不要在文档里粉饰过去）。

## 巡检

0. **定位目标。** 找到要维护的验证 skill：即正文中含有 launch/drive 章节和功能地图的项目本地 skill（通常是 `.cursor/skills/verify-*/`）。有多个候选 → 询问是哪一个；没有 → 停下来，指向 `/create-verification-skill`，而不是凭空造一个目标。

1. **索引清理。** 阅读功能地图 README，并 glob 其同级文件。修正缺失、多余、重复或失效的条目。轻量级；不生成清单。

2. **源码波次。** 每个功能文件启动一个只读子代理，并发运行。每个子代理从源码解释"这个面向用户的功能是如何工作的？"，标记可能的文档漂移并附引用，返回一条简洁的实时验证配方。子代理绝不驱动应用，也绝不编辑文件。返回结构：功能摘要 / 源码入口点 / 可能的漂移或无 / 一条配方。

3. **对齐。** 每个功能文件都有一份返回的摘要。将重叠的配方合并为尽可能少的应用状态。抽查所引用的漂移；不要重新证明干净的声明。扫一遍最近的改动，找出地图中缺失的面向用户的界面 —— 在判定某项缺失之前要求有具体的源码路径。

4. **实时巡检。** 即使源码看起来干净也必须进行。由协调者负责所有驱动；遵循验证 skill 自身的启动模型 —— 对于服务器和 UI，用单个长驻实例串行驱动；对于短生命周期的 CLI，每次驱动用全新的隔离会话（由该 skill 的 Launch 章节决定，而非本章节）。每个功能至少演练一次，并且无论发生什么失败，整个巡检过程都要保持三条不变量：(1) 绝不驱动一个自上次做出意外行为以来未做过健康检查的实例 —— 首次驱动前先 doctor，在以会话为单位的场景下每个新会话都 doctor，任何驱动失败后再次 doctor，而在 doctor 看不到失败的地方（健康进程上卡死的 UI 状态），重置到已知状态或重新启动，而不是寄希望于它自己恢复；(2) 迄今捕获的证据要能挺过每次清理，在其指定位置检查，而不是凭假设；(3) 任何驱动启动的东西都不能比该驱动的有效期活得更久 —— 失败迭代的残留要清理干净，无论会话是卡住、已退出还是共享的（对于共享实例，清理残留，而不是清理实例本身）。由 skill 漂移引起的 doctor 失败属于漂移：在编辑范围内修正它并重试一次 —— 只重启被该修正影响失效的东西，别做更多 —— 然后再判定本次巡检为 `blocked`。无法触达的功能只有在给出具体前置条件（认证、权限、操作系统、外部状态）和所尝试的路径时才能记为 `verified-unreachable`；如果地图遗漏了该前置条件，那就是漂移。分诊中的任何 harness 修正都要在提交前重新实时驱动一遍。最终拆除发生在本次运行最后一次驱动之后 —— 包括那些重新验证 —— 这样就没有东西能比本次运行活得更久（证据保留，按该 skill 的规定）。

5. **分诊。** 错误或缺失的用户视角描述 → 文档漂移，修正它。harness 无法驱动但功能正常的行为 → harness 缺口，修正它；harness 修正遵循与生成时相同的 helpers 规则（脚本需可执行，调用方式在 skill 正文中记录）。实际损坏的应用行为 → 产品缺口；为用户记录下来，不要放进这个 PR。

6. **提交或停止。** 对于 changed：提交一个包含经过证实的修正的 PR，先重新阅读每个改动过的文件。对于 clean 或 blocked：不开 PR，如实报告结果和覆盖情况。

在暂存位置保留简洁的运行笔记（覆盖的功能、无法触达的前置条件、确认的漂移、结果）；不要提交它们。

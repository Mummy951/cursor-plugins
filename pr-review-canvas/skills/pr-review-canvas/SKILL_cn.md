# PR 评审画布

构建一张画布，以有助于评审者理解的方式重新组织 PR diff 呈现——而非按文件树顺序排列。

## 前置条件

先阅读 `~/.cursor/skills-cursor/canvas/SKILL.md`。其中包含你必须遵循的生成策略、设计指引、slop 规则、自检以及文件路径约定。完整的组件和 hook 接口声明在 `~/.cursor/skills-cursor/canvas/sdk/index.d.ts` 及其同级的 `.d.ts` 文件中——阅读它们以了解准确的导出和 prop 结构，而不要靠猜测。

## 收集 diff

预期输入是一个 GitHub PR 链接（形如 `https://github.com/<owner>/<repo>/pull/<n>` 的完整 URL，或等价的 `gh` 可解析引用）。使用 `gh pr diff <pr>` 收集每个文件的路径、新增、删除和 hunk。

**如果用户没有提供 PR 链接，停下来询问。** 不要猜测当前分支、从近期历史推断，或退而使用本地 `git diff`。询问用户想要评审哪个 diff——具体的 PR URL 或编号——并在继续之前等待其回复。

## 按理解需要分组变更

**不要**按字母顺序或树状顺序呈现文件。按评审价值重新组织为有序的章节：

1. **核心逻辑**——新行为、算法变更、状态转换、API 接口变更。展示完整 diff 及周围上下文。
2. **接线与集成**——连接核心逻辑的路由注册、依赖注入、配置串联。精简呈现——足以确认正确性即可。
3. **样板与机械性变更**——导入重排、重命名、生成代码、格式化、类型重导出。以文件名和统计数据的列表形式总结。除非特别相关，否则不展示内联 diff。

以核心逻辑开头。评审者的注意力在顶部最集中。

## 将复杂逻辑提炼为伪代码

当某处核心变更涉及密集或错综复杂的逻辑——深层嵌套条件、状态机、重试/退避流程、多步转换——在 diff 旁添加一段简短的伪代码总结。伪代码应剥离语言语法、错误处理和样板代码，用几行揭示核心算法或控制流。这让评审者在阅读真实代码前先确认意图。

仅当实际 diff 难以快速浏览时才这样做。直白的变更不需要伪代码镜像。

## 用具体示例追踪棘手逻辑

伪代码展示变更的形态；示例追踪展示它的执行过程。当某个 hunk 以阅读代码难以预测的方式改变行为——重排的副作用、新的短路、改变的边界情况——选取一个具体输入，并排走过旧代码和新代码两条路径，突出它们分叉的步骤以及可观察的结果。保持输入小而真实。

仅将其用于真正令人意外的行为变更，而非每个核心 hunk。

## 引起对棘手之处的注意

当某个 hunk 包含令人意外、有风险或容易遗漏的内容时，在视觉上将其与周围 diff 分离，并配一个简短标签（如 "Subtle"、"Breaking"、"Race condition"、"Perf"）和一句话解释，让评审者同时看到关注点和代码。

将这些标注保留给真正棘手的项目——过度使用会破坏信号。

## 语气与内容

写面向评审者的评论，而非变更日志。聚焦于：
- 某事**为何**改变，而不只是改了什么。
- 文件之间的交互——例如 "`core.ts` 中的新校验器被 `routes.ts` 中新增的路由调用。"
- 任何 diff 本身无法明显体现的内容。

保持评论简洁。每条注释一到两句话。

## 发挥创意

上述章节是下限，而非上限。目标是为评审者提供理解这一具体变更的最快路径——因此看着眼前的 diff，思考哪种呈现方式真正有帮助。一个微型状态图、前后调用图、输入→输出对照表、提交时间线、每个文件的置信度标注、一个把所有其他内容折叠起来的大标注——任何适合该变更的形式都可以。

Canvas SDK 提供图表、表格、diff 视图、DAG 布局、卡片、统计、交互状态等更多能力。选用最服务于当前变更的组件。对重构的评审看起来不同于对 bug 修复的评审，也不同于对新功能的评审——让画布体现出这一点。

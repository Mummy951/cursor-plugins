# 热核级代码质量审查

当你需要进行一场异常严格的、聚焦于实现质量、可维护性、抽象质量和代码库健康度的审查时，使用此 skill。

最重要的是，本 skill 应当推动审查者在代码结构方面保持**雄心勃勃**。不要仅仅找出局部的清理机会。要主动寻找"code judo"（代码柔道）式的招法：那些在保留行为的同时，让实现变得显著更简单、更小、更直接、更优雅的重构。

## 核心提示词

从以下基线开始：

> 对当前分支的改动执行一次深度代码质量审计。
> 重新思考如何组织／实现这些改动，以便在不影响行为的前提下切实提升代码质量。
> 着力改进抽象、模块化，减少 Spaghetti 代码，提升简洁性与可读性。
> 要雄心勃勃，如果存在一条通过重构部分代码库来改进实现的清晰路径，就放手去做。
> 要极其彻底和严谨。三思而后行。

## 不可协商的附加标准

应用上述基线提示词，并加上以下明确的审查规则：

0. **在结构简化上保持雄心。**
   - 不要止步于"这里可以稍微干净一点"。
   - 寻找重新构造改动的机会，让整个分支、辅助函数、模式、条件或层级彻底消失。
   - 优先选择那种事后回看会让人觉得"本该如此"的方案。
   - 假定往往存在一个"code judo"招法可用：一种重组方式，能更有效地利用现有架构，让改动变得显著更简单、更优雅。
   - 如果你看到一条删除复杂度而非重新排列复杂度的路径，就强力推动那条路径。

1. **不要让一个 PR 在没有极充分理由的情况下，把文件从不足 1k 行推到超过 1k 行。**
   - 默认将其视为强烈的代码质量坏味道。
   - 优先提取辅助函数、子组件、模块或局部抽象，而不是任由文件膨胀超过 1000 行。
   - 如果 diff 跨过了该阈值，就明确询问是否应当先对该代码进行拆解。
   - 只有存在 compelling 的结构性理由，且最终文件仍然组织清晰时，才可豁免此条。

2. **不允许现有代码中出现随意的意大利面条式增长。**
   - 对新增的临时条件、散落的特殊案例，或被插入无关流程中的一次性分支保持高度警惕。
   - 如果一项改动加入了"在随机位置出现的奇怪 if 语句"，要将其视为设计问题，而非风格上的吹毛求疵。
   - 优先把逻辑推入专门的抽象、辅助函数、状态机、策略对象或独立模块，而不是把现有路径搅得一团乱。
   - 要点明那些让周边代码更难推理的改动，即便它们在技术上是能跑通的。

3. **倾向于清理设计，而不只是接受能跑的代码。**
   - 如果行为可以保持不变，而结构能变得明显更干净，就推动更干净的版本。
   - 不要对那些让代码库变得更混乱的"能用就行"实现盖通过章。
   - 强烈偏好那些彻底移除活动部件的简化，而非仅仅把同样的复杂度四处摊开的重构。

4. **偏好直接、平淡、可维护的代码，而非取巧或"魔法"式的代码。**
   - 把脆弱、临时拼凑或"魔法"般的行为视为代码质量问题。
   - 对那些掩盖简单数据形态假设的通用机制保持怀疑。
   - 标记那些只增加间接层却不带来清晰度收益的薄抽象、身份包装器或透传辅助函数。

5. **当类型和边界的整洁度影响可维护性时，要强力推动。**
   - 当本可以存在更清晰的类型边界时，质疑不必要的可选性、`unknown`、`any` 或大量强制类型转换的代码。
   - 优先使用显式的类型模型或共享契约，而非松散形态的临时对象。
   - 如果某个分支依赖静默回退来掩盖某个不清晰的不变量，就询问是否应当改为显式化该边界。

6. **让逻辑留在规范层级，并复用现有辅助函数。**
   - 点明功能逻辑渗漏进共享路径，或实现细节透过 API 泄漏出来的情况。
   - 优先使用现有的规范工具／辅助函数，而非定制的一次性实现。
   - 把代码推向正确的包、服务或模块，而不是纵容架构漂移成为常态。

7. **当更干净的结构显而易见时，把不必要的顺序编排和非原子更新视为设计坏味道。**
   - 如果彼此独立的工作无缘无故地被串行化，就询问该流程是否应当改为并行执行。
   - 如果相关更新可能让状态停留在半应用状态，就推动更原子的结构。
   - 不要过度纠结微优化，但确要点明那些让实现更脆弱的、本可避免的编排复杂度。

## 主要审查问题

对每一项有意义的改动，都要问：

- 是否存在一个"code judo"招法，能让这里显著更简单？
- 这项改动能否被重新构造，从而需要更少的概念、分支或辅助层？
- 这是改善还是恶化了局部架构？
- diff 是否在本应有更好抽象的地方增加了分支复杂度？
- 某个原本内聚的模块是否变得更耦合、更有状态、或更难快速浏览？
- 这段逻辑是否位于正确的文件和层级？
- 这项改动是否把某个文件或组件撑大了，超出了健康的大小边界？
- 是否存在重复的条件，暗示着缺失的模型或缺失的辅助函数？
- 实现是直接且易读的，还是依赖特殊案例和 incidental 控制流？
- 这个抽象是否真的物有所值，抑或只是一个包装器？
- diff 是否引入了强制类型转换、可选性或临时对象形态，掩盖了真正的不变量？
- 这段逻辑是位于规范层级，还是 diff 让细节跨越了边界泄漏出去？
- 这个编排是否比实际需要更顺序化、或更不原子化？

## 要激进标记的内容

当你看到以下情况时，升级问题级别：

- 一个复杂的实现，而更干净的重新构造本可以删除整类复杂度。
- 那些搬来搬去代码、却未能减少读者脑中必须持有的概念数量的重构。
- 因该 PR 而跨越 1000 行的文件，尤其是当新代码本可以被拆分出去时。
- 被硬栓到无关代码路径上的新条件。
- 让现有控制流复杂化的一次性布尔值、可空模式或标志位。
- 渗漏进通用模块的功能专属逻辑。
- 掩盖简单结构、让代码更难推理的通用"魔法"处理。
- 只增加间接层却不带来任何简化的薄包装器或身份抽象。
- 不必要的强制类型转换、`any`、`unknown` 或可选参数，混淆了真正的契约。
- 复制粘贴的逻辑，而非提取出的辅助函数。
- 在一个本已繁忙的函数中部实现的狭窄边界案例处理。
- 技术上通过了测试、却让代码更不模块化或更不易读的重构。
- 很可能变成长期债务的"临时"分支。
- 代码库中已有该工作的规范工具，却仍定制辅助函数。
- 在错误层级／包中加入的逻辑，而它本应位于更中心的位置。
- 顺序执行的异步流程，而其中明显独立的工作若并行执行本可更简单、更清晰。
- 让状态比必要程度更不原子化的部分更新逻辑。

## 首选的补救方案

当你识别出代码质量问题时，优先给出如下建议：

- 删除整个间接层，而不是去打磨它。
- 重新构造状态模型，让条件消失，而不是把它们集中起来。
- 改变所有权边界，使该特征成为现有抽象的自然延伸。
- 把特殊案例逻辑变成异常更少的、更简单的默认流程。
- 提取一个辅助函数或纯函数。
- 把一个大文件拆分为更小、更聚焦的模块。
- 把功能专属逻辑移到专门抽象之后。
- 用类型模型或显式分发器替换条件链。
- 把编排与业务逻辑分离。
- 把重复分支合并为一条更清晰的流程。
- 删除那些并未切实让 API 更清晰的包装器。
- 复用现有的规范辅助函数，而非引入一个近乎重复的实现。
- 让类型边界更显式，从而让控制流更简单。
- 把逻辑移到已经拥有该概念的包／模块／层级。
- 当并行化也能简化编排时，就并行化独立的工作。
- 当部分状态会更难推理时，把相关更新重组为更原子的流程。

当真正的问题是结构性的时，不要满足于"也许把这个重命名一下"这样的反馈。
如果存在通往一个简单得多的思路的可行路径，就不要满足于同一堆乱糟糟思路的一个稍微干净些的版本。

## 审查语气

要直接、严肃，并对质量严格要求。
可以不必粗鲁，但也不要把重大的可维护性问题软化为温和的建议。
如果代码正在让代码库变得更混乱，就明确说出来。
如果实现错失了一次大幅简化的机会，也同样明确说出来。

好的措辞示例：

- `this pushes the file past 1k lines. can we decompose this first?`
- `this adds another special-case branch into an already busy flow. can we move this behind its own abstraction?`
- `this works, but it makes the surrounding code more spaghetti. let's keep the behavior and restructure the implementation.`
- `this feels like feature logic leaking into a shared path. can we isolate it?`
- `this abstraction seems unnecessary. can we just keep the direct flow?`
- `why does this need a cast / optional here? can we make the boundary more explicit instead?`
- `this looks like a bespoke helper for something we already have elsewhere. can we reuse the canonical one?`
- `i think there's a code-judo move here that makes this much simpler. can we reframe this so these branches disappear?`
- `this refactor moves complexity around, but doesn't really delete it. is there a way to make the model itself simpler?`

## 输出预期

按以下顺序优先排列发现的问题：

1. 结构性代码质量退化
2. 错失的大幅简化／code-judo 重构机会
3. 意大利面条式／分支复杂度的增加
4. 让代码更难推理的边界／抽象／类型契约问题
5. 文件大小与拆解方面的顾虑
6. 模块化与抽象问题
7. 可读性与可维护性问题

如果存在更大的结构性问题，不要用大量低价值的吹毛求疵淹没审查意见。
相比一长串表面化的意见，宁可给出数量更少、但确信度更高的评论。

## 通过门槛

不要仅仅因为行为看起来正确就予以通过。
通过的标准是：

- 没有明显的结构性退化
- 当存在一条清晰路径时，没有错失让实现显著更简单的明显机会
- 没有不正当的文件体积膨胀
- 没有因特殊案例分支导致的明显意大利面条式增长
- 没有让代码更难推理的、明显取巧或"魔法"式的抽象
- 没有混淆真正设计的不必要包装器／强制类型转换／可选性改动
- 没有明显的架构边界泄漏，或本可避免的规范辅助函数重复
- 没有错失那些能切实改善可维护性的明显拆解机会

除非作者能清晰说明理由，否则将以下各项视为推定性的阻塞项：

- 在存在可行的 code-judo 招法能删除复杂度的情况下，该 PR 却保留了大量 incidental 复杂度
- 该 PR 把一个文件从不足 1000 行推到了 1000 行以上
- 该 PR 加入了临时分支，让现有流程更加纠缠
- 该 PR 通过把功能检查散落到共享代码中来解决局部问题
- 该 PR 加入了不必要的抽象、包装器或大量强制类型转换的契约，让设计变得更间接
- 该 PR 重复了现有辅助函数，或在存在明确规范归属时把逻辑放在了错误的层级

如果这些条件未得到满足，就留下明确、可操作的反馈，并推动进行更干净的拆解。

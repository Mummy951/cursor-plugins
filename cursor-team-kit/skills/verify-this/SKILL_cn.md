# 验证此项

验证不是复述。它是用可重复的证据证明或推翻一项具体主张。

## 何时使用

- 用户要求"验证这个"、"证明它有效"、"这个修复起作用了吗"或"给我看证据"。
- 一个 bug 修复需要做修复前/修复后的复现。
- 一项关于 UI、CLI、API、性能或内存的主张需要测量。
- 测试通过了，但用户可见的行为仍需确认。

不要把它用于"代码更整洁了"这类含糊的主张。先要求一个可测量的主张。

## 工作流程

1. 以可证伪的形式重述主张：条件、指标和阈值。
2. 挑选能够推翻它的最小本地切面。
3. 从旧状态采集基线：合并基、父提交、失败的分支，或当前已损坏的复现。
4. 用相同的命令、数据、预热和环境，从改动后的状态采集处理后数据。
5. 比对原始产物：数字、截图、终端记录、HTTP 响应、性能分析、堆快照或测试输出。
6. 只返回一个结论：`VERIFIED`、`NOT VERIFIED` 或 `INCONCLUSIVE`。

## 本地切面

- 代码行为：聚焦的单元/集成测试或最小复现脚本。
- CLI/TUI 行为：`control-cli`、终端记录或演示录像。
- UI 行为：`control-ui`、截图、无障碍快照或浏览器追踪。
- API 行为：本地 HTTP/RPC 请求与响应差异。
- 性能：同机基线/处理用时或 CPU 性能分析。
- 内存：可疑操作前后的堆快照。

## 产物布局

当可以安全地写入产物时：

```text
/tmp/verify-this/<claim-slug>/
├── claim.md
├── timeline.md
├── baseline/
├── treatment/
├── diff/
└── verdict.md
```

如果产物可能包含敏感代码、提示词、截图、HTTP 正文或堆数据，除非用户同意存储到磁盘，否则只保留最小的内联证据。

## 结论规则

- `VERIFIED`：基线与处理后在预测方向上存在差异，达到主张的阈值，且没有明显的混杂因素。
- `NOT VERIFIED`：行为未变、朝错误方向变化，或未达到阈值。
- `INCONCLUSIVE`：没有有效的基线、信号嘈杂、测量失败，或环境差异使比对失效。

## 输出

使用以下格式：

```text
VERIFIED | NOT VERIFIED | INCONCLUSIVE
主张：<可证伪的主张>

证据：
<指标/产物>：baseline=<...>，treatment=<...>，delta=<...>，threshold=<...>

推理：
<一段紧凑的文字，指出证据及任何混杂因素>
```

不要弱化负面结果。一个明确的 `NOT VERIFIED` 是有价值的。
